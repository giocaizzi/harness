# Finish: verify, ship, land, deploy, record

## Checklist

Keep the run's checklist in `.factory/runs/N/checklist.md` of the main checkout (git-ignored, so it never enters the diff): acceptance checks with their state, open fold-ins, what is pushed, routing deviations with their reasons, and each step's start and end time in UTC as you enter and leave it (the source of `phases`). Update it as you go; after a compaction or a resume, read it before anything else.

## Verify

A fresh-context `verifier` (this plugin's agent) gates the change; it must not be you. It runs on the pushed branch, before the PR opens. Brief it with the ticket (`<owner>/<repo>#N`), the branch, the plan and log comments, the round, and the verdict path `.factory/runs/N/verdict-<round>.md` in the main checkout.

- **Where:** a subagent where the harness has one (`factory:verifier` in Claude Code; the `verifier` agent in Copilot CLI, VS Code, Codex and opencode; the `subagent` tool on pi). Elsewhere, a separate headless session in the worktree, given the agent's prompt and the brief.
- **Model and effort:** the verify rows of [routing.md](routing.md), by change risk and size; Claude Code takes their overrides on the spawn. Where a harness fixes effort in the agent definition (Codex: `model_reasoning_effort` in the agent TOML; Copilot: per-agent `effortLevel` in user settings), a `high` verify is not reachable from the spawn: run it as a separate session at `high`, or accept `medium` and record the deviation with that reason.
- **Verdict file:** the verifier writes its report there (through Bash where it has no Write tool); it never posts or hands back. Its first line names the head SHA it covers. Once the PR exists, post each verdict verbatim as a `factory:verdict <round>` comment on it, and add links to the verdicts to the PR body (edit it once they are posted).
- **Rounds:** a `dev-tools:driver` spawn fixes what it reports (brief: the verdict file and the worktree), then the verifier re-reviews only the new diff; at most three rounds in all, the scoped rounds after a pass included (why three: the verifier's definition). Still failing, or a fourth round due: ask on the ticket with its findings and park.
- **After a pass:** a comment-only or doc-only fix needs no new round. Any code change needs a scoped round on that delta only.
- **Merge gate:** a passing verdict whose head SHA is the PR head. Commits after it go through `land` step 2 (the hub's check and the landing note); a code change among them also needs its scoped round (After a pass).

## Ship and land

`ship`, plus these factory sections when the repo has no PR template: the body carries `## Scope` (the decision log), the acceptance evidence as the testing under `## Verification`, `## Risk` (tier and why) and `## How to revert`, with `Closes #N` among the footers. List each existing test assertion the change altered as one line under `## Verification`: `Existing tests changed: <test> (<old> → <new>, per AC<n>)`; a flipped assertion stays visible without a decision row. Then land by the change's risk tier (the highest `risk` tier any changed path matches; unmatched paths are medium):

- `merge: auto`: `land`.
- `merge: owner`: ask on the ticket for the merge (`Ready to merge: #<pr>`, with the evidence) and park. The next run resumes once an approver merged the PR: read `merged_by.login` (`gh api repos/{owner}/{repo}/pulls/<pr> --jq .merged_by.login`) and compare it with `approvers`, ignoring case. A merge by anyone else (a writer who is not an approver, a bot) leaves the ticket parked: say who merged on the ticket and stop.
- Any change under `.factory/` (the config, and with it the approvers) is `merge: owner` whatever tier its paths match, even when the repo maps them to `auto`.

## Deploy and live-verify

This is `land`'s verify-where-it-lands step, made concrete by the config. Only for components with `deploy` in the config. With the merge commit as `$SHA` (`gh pr view <pr> --json mergeCommit --jq .mergeCommit.oid`), run `deploy.wait`, then each `deploy.verify`, and post their output or run links as evidence on the ticket. Secrets they need come by reference (config `secrets`, through `secrets-handling`), never as values.

A failed live check means the change does not work where it lands: open a revert PR of the merge commit, land it by the same tier, then ask on the ticket with the findings and park. `deploy.rollback` is for when the config names a command and a revert is not enough. A check that needs access you lack parks with the exact command for the owner.

## Record

Every run that passed the gate ends with a result file and a result comment, in this order, and then releases its claim (a stop at the gate: **Gate stops** below):

1. Write `.factory/runs/N/result.json` with this skill's `scripts/write-result.mjs`, never by hand: put the judgment fields (below) in a JSON file, such as `.factory/runs/N/judgment.json` in the main checkout, and run `node <skill dir>/scripts/write-result.mjs [--ticket <owner>/<repo>#N] [--run-id <claim's run id>] <file>` (`-` reads stdin) from the repo or its worktree. It fills `schema`, `ticket`, `run_id`, `mode`, `host.name`, `host.os` and `finished_at` (the time of this write), checks the whole file, and writes nothing while anything is wrong: exit 1 lists every error, so fix the input (never the written file) and run it again until it exits 0; exit 2 is a usage or environment problem (no ticket, not in a git checkout). The result comment is not yet in `posts`.
2. Post the result comment (kind `factory:result`, [comments.md](comments.md#comments)).
3. Add the comment with `node <skill dir>/scripts/write-result.mjs [--ticket <owner>/<repo>#N] --post result=<comment URL>`: it appends `{kind, url, state: posted}` to `posts` (an entry already listed with that URL becomes `posted`), leaves `finished_at` as step 1 set it, and checks the file again. This edit finalizes the file.

`.factory/runs/N/result.json` sits in the main checkout, which outlives the worktree (the parent of `git rev-parse --path-format=absolute --git-common-dir`); the script finds it from any worktree. For a shell write there (the judgment file, the checklist) spell the path as a literal absolute path or `$(git rev-parse --path-format=absolute --git-common-dir)/../.factory/runs/N/…`, as the guard reads no nested substitution. Keys: `schema` (2), `ticket`, `run_id`, `end_state`, `reason`, `reason_code`, `pr`, `decisions` (the log rows: `item`, `test`, `decision`, `where`), `evidence`, `checks` (`command`, `result`), `follow_ups`, `posts` (`kind`, `url`, `state`), `phases` (`name`, `started_at`, `ended_at`), `verifier` (`verdict`, `rounds`), `routing` (`phase`, `policy_model`, `policy_effort`, `model`, `effort`, `deviation_reason`), `mode`, `cost_usd`, `tokens`, `turns`, `harness`, `model`, `effort`, `sessions` (`role`, `id`, `model`, `effort`), `plugin_versions`, `host` (`name`, `os`, `runner`), `finished_at`; their meaning is in `docs/factory.md` (Result contract). The judgment file holds every key but the ones the script fills (`schema`, `ticket`, `run_id`, `mode`, `finished_at`, and `host` but its `runner`); it rejects any of those, and any other key, in the input. `host.runner` is `runtime` when `FACTORY_RUN_ID` is set, else `attended`; give it in the input only for a `headless` run (the script refuses `runtime` without `FACTORY_RUN_ID`, and any other runner with it). `--run-id` takes 1 to 128 printable characters.

Record what the harness reports, not what you asked for: a model or effort that differs from the requested one is how a silent downgrade shows. Fields the harness does not expose are `null`. `end_state` is `budget_reached` when a budget cap stopped the run, which is not a failure; never write `halted`, which only a runtime writes (the script rejects it).

- **`run_id`:** the script fills it, and the claim comment uses the same id: `FACTORY_RUN_ID` when it is set, so the result matches the runtime's claim. Else `FACTORY_ATTENDED_RUN_ID` when it is set and `FACTORY_ATTENDED_TICKET` is this ticket (`<owner>/<repo>#N`, compared ignoring case, as GitHub names are): the session was started with this skill's `scripts/attended.sh` (or `attended.ps1`), which tagged its telemetry with that id, so the claim comment carries it too. When `FACTORY_ATTENDED_TICKET` names another ticket, ignore both (the script warns) and tell the person the session's telemetry is tagged for that other ticket. Otherwise (no launcher, or that mismatch) the main session's id where the harness exposes one, else `<host>-<number>-<UTC timestamp>`, chosen at the claim: pass it as `--run-id`, so the result carries the claim's id rather than a new one.
- **`reason_code`:** the park or failure as one code, `null` when done or none fits; the specific cause wins over `question` when a park also asks one: a question `question`, the M+ plan waiting for the OK `plan_gate`, an owner merge `merge_gate`, the third park `grooming`, the verifier still failing after three rounds `verify_rounds`, a failed live check `live_verify_failed`, missing access or a broken environment `env_blocked` (one denied call is not enough: retry it as a simpler single command inside the checkout first, and only a required step with no allowed path counts), a budget cap `budget`, a credential or token failure, or a runtime-started run with no trusted claim under its run id, `auth`; never `takeover`, which only a runtime writes (the script rejects it).
- **`phases`:** one entry per step reached, in order (`gate`, `plan`, `work`, `verify`, `ship`, `deploy`, `record`), each with both `started_at` and `ended_at` as ISO 8601 UTC times; `ended_at` is `null` for the step the run stopped in. Take them from the checklist; for a step it lacks (a compaction, a resumed run), from the timestamps the run already has, each step ending where the next starts:
  - `gate`: from the run's start (its claim comment's `created_at` when it posted one).
  - `plan`: to the plan comment's `created_at`, or for M and larger the owner's OK.
  - `work`: to the last pushed commit (`git log -1 --format=%cI` on the branch).
  - `verify`: to the passing verdict (its file's time, or its `factory:verdict` comment's `created_at`); all rounds are one step, their count is in `verifier`.
  - `ship`: to the merge, merge wait included (`gh pr view <pr> --json mergedAt`).
  - `deploy`: from `deploy.wait` to the last `deploy.verify`.
  - `record`: to `finished_at`; leave its `ended_at` `null` and the script sets it.

  A time you cannot find is `null`, never a guess and never a dropped key or entry; say which one and why in the report. Note each time in the checklist as `date -u +%Y-%m-%dT%H:%M:%SZ` prints it (PowerShell: `(Get-Date).ToUniversalTime().ToString('yyyy-MM-ddTHH:mm:ssZ', [cultureinfo]::InvariantCulture)`).
- **`finished_at`:** the script fills it with the UTC time it writes the file (step 1), never `null`; `--post` keeps it.
- **`routing`:** optional, one entry per spawned phase: the policy's model and effort from [routing.md](routing.md) next to what actually ran. `deviation_reason` is required, non-empty, whenever `model` or `effort` differs from the policy's, else `null`. Note each deviation and its reason in the checklist as it happens.
- **`mode`:** the script fills it: `"mode": "dev"` when `FACTORY_DEV=1` is set, else no key. The check rejects any other value.
- **`verifier`:** its last verdict and the number of rounds; `null` when the run stopped before the verifier.

`ticket` is the string `<owner>/<repo>#<number>`, never a bare number, and equals `FACTORY_TICKET` exactly (case-sensitive) when that is set. The script fills it from `FACTORY_TICKET`, else `--ticket`, else the launcher's `FACTORY_ATTENDED_TICKET`; with none it stops (exit 2), and a `--ticket` that differs from `FACTORY_TICKET` is refused. Its check (also `scripts/check-result.mjs <result.json>` alone) rejects a `schema` other than 2, an empty `run_id` or one that differs from `FACTORY_RUN_ID` when that is set, an `end_state` other than `done`, `parked`, `failed`, `budget_reached` or `halted` (a runtime's), a `reason_code` that is neither `null` nor one of the codes above (`takeover` counts, for a runtime's results), a `reason` that is not a string, a `ticket` that is not that string, a missing or impossible `finished_at`, empty or out-of-order `phases`, a phase entry that is not an object, a missing time key, a deviation without its reason and a `mode` other than `dev`.

**Gate stops.** A run a runtime started (`FACTORY_RUN_ID` set) that stops at the gate still writes `result.json`, with `end_state` `failed`, the gate check that failed as `reason`, and `reason_code` `auth` when no trusted claim carries this run's id ([comments.md](comments.md#gate), whether or not the stop names a login), else the code that fits or `null`; `phases` holds `gate` alone. It does step 1 of the Record order (write with `write-result.mjs`) but posts no result comment, so `posts` holds none, and leaves the claim label, which it never took: the runtime reads the file and releases its own claim. The Ready check is no stop: without acceptance criteria or a proof command the run asks on the ticket and parks (`parked`, `question`) like any question. An attended run that stops at the gate tells the person and writes nothing.

A parked ticket keeps its worktree and pushed branch for the next run.
