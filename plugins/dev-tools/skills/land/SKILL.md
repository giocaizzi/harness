description: Wait for CI on a PR, fix trivial failures, merge it through auto-merge or the merge queue (a direct squash merge once every check passed where auto-merge is unavailable), then sync main, remove the branch and worktree, and verify the change works where it lands. Use when the user asks to merge, land or verify a PR, or types /land or /verify (optionally a PR number).

# Land

Take an open PR (GitLab: MR) to merged and clean. Argument: a PR number, or several; default is the current branch's PR. Detect the forge and take its commands from the `repo-standard` mapping; on GitHub also follow `github-workflow`. The argument is the text after the skill name, repeated here when the harness fills it in: $ARGUMENTS

**Several approved PRs land together, never one after another.** On GitHub run `${CLAUDE_PLUGIN_ROOT}/skills/land/scripts/land-many.sh <n>...` (`.ps1` on Windows; behaviour and exits in its header): it applies step 2's gate (no check failing on the head, every required one passed, no workflow run on that head still running), waits out gh's `Required status check ... is expected` refusal like a pending check, enqueues or arms each PR as in step 4, re-enqueues one that falls out, sends a PR gh refuses as part of a stack through the asynchronous merge API (step 3), and prints one line per PR as it ends. Act on each line at once, without waiting for the rest: a `DIRTY` or `BEHIND` PR is updated, built on the merged tree (every package including tests: `go vet ./...`, `tsc --noEmit`, the language's equivalent) and re-landed, a `FAILED` one goes back through step 1, a `STACKED` one (based on another PR's branch) lands with `gh stack merge` or through step 3. A PR marked ready after a draft run starts new runs on the same head: from then on the merge queue, or the check the ready run reports, is the real gate, not the earlier draft check. It arms and enqueues pinned to the head its checks passed on (`--match-head-commit`, the enqueue's head), so pass it only PRs whose current head is the approved or proven one. The hub arms each PR as soon as its verdict is on the current head and CI is green, never waiting for another PR to merge first. Then run steps 6 and 7 per merged PR.

1. **Watch CI** (GitHub `gh pr checks --watch`, GitLab `glab ci status --live`, Azure DevOps `az repos pr policy list`). On failure, fix lint or format problems with a new commit and push; for anything else, stop and report the failing job and its log.
2. **Merge only when every check passed.** Never merge on a failing or missing check, even if branch protection would not stop you; a red check on `main` is fixed first, in its own PR.
   **Commits after approval:** compare the PR/MR head with the head the reviewer approved. Each commit added since gets a hub check before landing: read its diff and confirm it is what was announced. A pure merge of the default branch is proven by `${CLAUDE_PLUGIN_ROOT}/skills/land/scripts/verify-merge-only.sh <approved-sha> <head-sha>` (`.ps1` on Windows; full SHAs from `gh pr view <n> --json headRefOid` and the verdict, never ref names; behaviour in its header), which prints the landing note: `git merge-tree --write-tree` must redo the merge without a conflict and give exactly the pushed tree (it replaced a `git patch-id` comparison, which a merge moving the PR's hunk to an identical block passed). Run it from a plain clone with git 2.40 or newer: attributes come from the approved tree, the global and system config are ignored, and it refuses a shallow clone, a non-empty `.git/info/attributes` or a merge driver in the repo config, which could resolve a conflict on the verifier's side. A non-zero exit, a conflict resolution, any other commit, or a PR on another base goes back to review as a new round on the delta; after round 2, stop and ask the owner instead (`github-workflow`, Landing a change, rule 8).
   **Landing note:** before merging, comment on the PR/MR with the approved SHA, the head being merged, and what was checked for each post-approval commit, so the history records why an unreviewed commit was acceptable. For a pure merge of the base the script prints the note text; otherwise the hub writes it.
   **Merge helpers:** never push from an author's worktree, which may hold unpushed, unreviewed commits. Sync a PR/MR branch from a fresh detached worktree at the pushed head, and check the result's first parent is that head before pushing.
3. **Retarget stacked children first.** Before arming the merge, list PRs based on this branch (`gh pr list --base <branch>`, `glab mr list --target-branch <branch>`, `az repos pr list --target-branch <branch>`) and retarget each to the default branch, with its auto-merge off until this PR merges; siblings (several PRs that each need this one but not each other) are all children, so retarget every one: deleting this branch on merge can close a child whose base disappears. After the squash, merge the default branch into each child before landing it; the steps, and the recovery for a child already closed, are in `github-workflow` (Stacks without `gh stack`).
   **After an integration branch was squash-merged,** a branch that carries its history conflicts on every file both touched. Run `${CLAUDE_PLUGIN_ROOT}/skills/land/scripts/resync-after-squash.sh <last-integration-sha> [<base>]` on it (`.ps1` on Windows): it merges the base keeping the branch's tree, applies only the base's changes since that sha, and exits non-zero unless the merge changed exactly the files the base changed.
   **A PR in a native stack** (`gh stack`; gh refuses it with `part of a stack and must be enqueued using the asynchronous merge REST API`): the legacy `gh pr merge` cannot merge or enqueue it. Enqueuing or merging it needs the asynchronous merge API, which lands the whole stack up to and including that PR atomically: `gh stack merge <n>`, or `gh api -X PUT repos/{owner}/{repo}/pulls/<n>/merge-async -H 'X-GitHub-Api-Version: 2026-03-10' -f merge_action=merge_queue -f sha=<head>` (no queue: `-f merge_action=default -f merge_method=squash`), then poll `gh api repos/{owner}/{repo}/pulls/<n>/merge-async/<uuid>` until `status` is `merged`, `enqueued` (queued, not merged: wait on the PR) or `failed`. A stack lands bottom-up (`github-workflow`, Landing a change, rule 4); details in `github-workflow` (Stacked PRs).
4. **Merge without bypassing** through the forge's auto-merge (`gh pr merge --auto --squash --match-head-commit <sha>`, with `<sha>` the head the verdict names or the script proved: gh arms only when the head is that SHA; `glab mr merge --auto-merge --squash`, `az repos pr update --auto-complete true --squash true`), or enqueue when a merge queue exists. Never use `--admin`, `--bypass-policy` or disable a rule. Never push to an armed or queued PR (`github-workflow`, Landing a change, rule 9): disarm, push, re-verify, re-arm.
   **Auto-merge unavailable** (GitHub only; for example a private repo on the Free plan): when the forge reports it (`gh api repos/{owner}/{repo} --jq .allow_auto_merge` prints `false`, or arming fails with `Auto merge is not allowed for this repository`) and the repo has no merge queue (a queue gives the same error; enqueue instead), merge directly once `gh pr checks <n> --watch` exits 0 with every check passed: `gh pr merge <n> --squash --match-head-commit <sha>`, with the head SHA the checks ran on. Never enable the repo setting or add `--admin` to get there; if the plain merge is refused, stop and report why.
5. **Wait until it ends, however it ends**, never on merged alone: a failed required check leaves an armed PR open for good, and a loop on its state never returns. On GitHub run `${CLAUDE_PLUGIN_ROOT}/skills/land/scripts/wait-pr.sh <n>` (unrendered: `scripts/` under the path this skill was loaded from; `.ps1` on Windows; exits and options in its header): it returns on merged, closed, a failed required check, a branch behind or in conflict, or its timeout. Its `--timeout` is the deadline in the background, never the tool's (see `subagent-orchestration`, Waiting on other agents). On any exit but merged, act on what it printed (step 1, update the branch, or report); once merged, `git pull --ff-only` on the default branch.
6. **Clean up:** `git worktree remove <path>` for this task's worktree, never `--force`; if it refuses, report what is left in the worktree (`git -C <path> status --short`) and stop. Then delete the local branch and `git worktree prune`. Run each as its own command once the PR shows merged, never chained after `gh pr merge` or in one long chain: a guard checks a branch delete against the merged PR before the command runs, so in the same chain as the merge it finds none and asks, and it denies a risky step buried in a chain of more than 3 commands.
   A PR closed without merging keeps its remote branch (GitHub deletes only on merge): delete it (`git push origin --delete <branch>`) once no child is based on it.
7. **Verify where it lands.** Merged is not working: wait for whatever the merge triggers, then prove the change took effect with one check that reads the real target, not the repo. For example:
   - a deployed service: the deploy or release run finished green, then its health endpoint or service status;
   - dotfiles: `chezmoi diff` is empty after apply, and the changed line is in the rendered file;
   - a plugin or extension: the marketplace or package update ran, and the installed version is the new one;
   - a library: the release and tag exist with the new version.
   When the check needs access you lack or a step the user runs, say so and give the exact command.

Report the merge commit, the verify evidence (command and result) or what was skipped and why, and anything left behind.
