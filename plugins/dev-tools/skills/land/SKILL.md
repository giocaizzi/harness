# Land

Take an open PR (GitLab: MR) to merged and clean. Argument: a PR number, or several; default is the current branch's PR. Detect the forge and take its commands from the `repo-standard` mapping; on GitHub also follow `github-pull-requests`. The argument is the text after the skill name, repeated here when the harness fills it in: $ARGUMENTS

**Several approved PRs land together, never one after another.** On GitHub run `${CLAUDE_PLUGIN_ROOT}/skills/land/scripts/land-many.sh <n>...` (`.ps1` on Windows; behaviour and exits in its header): it applies step 2's gate (no check failing on the head, every required one passed, no workflow run on that head still running; a cancelled run superseded by a newer, non-skipped run of the same check (name, workflow, event) is not a failure, while a cancelled newest run (it waits while its workflow still runs on the head, then fails), any failure, timeout or `action_required`, or a missing required check still blocks), waits out gh's `Required status check ... is expected` refusal like a pending check, enqueues or arms each PR as in step 4, re-enqueues one that falls out, sends a PR gh refuses as part of a stack, and a layer of a native stack based on another branch, through the asynchronous merge API (step 3: one request on the stack's top layer covers the batch's other layers, and a refusal naming a required check `in progress` or `expected` is waited out and requested again), and prints one line per PR as it ends. Act on each line at once, without waiting for the rest: a `DIRTY` or `BEHIND` PR is updated, built on the merged tree (every package including tests: `go vet ./...`, `tsc --noEmit`, the language's equivalent) and re-landed, a `FAILED` one goes back through step 1, a `STACKED` one (based on another PR's branch and in no native stack) is retargeted through step 3. A PR marked ready after a draft run starts new runs on the same head: from then on the merge queue, or the check the ready run reports, is the real gate, not the earlier draft check. It arms and enqueues pinned to the head its checks passed on (`--match-head-commit`, the enqueue's head), so pass it only PRs whose current head is the approved or proven one. The hub arms each PR as soon as its verdict is on the current head and CI is green, never waiting for another PR to merge first. Then run steps 6 and 7 per merged PR.

1. **Watch CI** (GitHub `gh pr checks --watch`, GitLab `glab ci status --live`, Azure DevOps `az repos pr policy list`). On failure, fix lint or format problems in one new commit and push once (never an empty commit to re-trigger CI; `github-pull-requests`, Landing a change, rule 1); for anything else, stop and report the failing job and its log.
2. **Merge only when every check passed.** Never merge on a failing or missing check, even if branch protection would not stop you; a red check on `main` is fixed first, in its own PR.
   **Commits after approval:** compare the PR/MR head with the head the reviewer approved. Each commit added since gets a hub check before landing: read its diff and confirm it is what was announced. A pure merge of the default branch is proven by `${CLAUDE_PLUGIN_ROOT}/skills/land/scripts/verify-merge-only.sh <approved-sha> <head-sha>` (`.ps1` on Windows; full SHAs from `gh pr view <n> --json headRefOid` and the verdict, never ref names; behaviour in its header), which prints the landing note: `git merge-tree --write-tree` must redo the merge without a conflict and give exactly the pushed tree (it replaced a `git patch-id` comparison, which a merge moving the PR's hunk to an identical block passed). Run it from a plain clone with git 2.40 or newer: attributes come from the approved tree, the global and system config are ignored, and it refuses a shallow clone, a non-empty `.git/info/attributes` or a merge driver in the repo config, which could resolve a conflict on the verifier's side. A non-zero exit, a conflict resolution, any other commit, or a PR on another base goes back to review as a new round on the delta; after round 2, stop and ask the owner instead (`github-pull-requests`, Landing a change, rule 8).
   **Landing note:** before merging, comment on the PR/MR with the approved SHA, the head being merged, and what was checked for each post-approval commit, so the history records why an unreviewed commit was acceptable. For a pure merge of the base the script prints the note text; otherwise the hub writes it.
   **Merge helpers:** never push from an author's worktree, which may hold unpushed, unreviewed commits. Sync a PR/MR branch from a fresh detached worktree at the pushed head, and check the result's first parent is that head before pushing.
3. **Retarget stacked children first.** Before arming the merge, list PRs based on this branch (`gh pr list --base <branch>`, `glab mr list --target-branch <branch>`, `az repos pr list --target-branch <branch>`) and retarget each to the default branch, with its auto-merge off until this PR merges; siblings (several PRs that each need this one but not each other) are all children, so retarget every one: deleting this branch on merge can close a child whose base disappears. After the squash, merge the default branch into each child before landing it; the steps, and the recovery for a child already closed, are in `github-pull-requests` (Stacks without `gh stack`).
   **After an integration branch was squash-merged,** a branch that carries its history conflicts on every file both touched. Run `${CLAUDE_PLUGIN_ROOT}/skills/land/scripts/resync-after-squash.sh <last-integration-sha> [<base>]` on it (`.ps1` on Windows): it merges the base keeping the branch's tree, applies only the base's changes since that sha, and exits non-zero unless the merge changed exactly the files the base changed.
   **A PR in a native stack** (`gh stack`; its REST object has a non-null `stack`; `gh pr merge` refuses it with `part of a stack and must be enqueued using the asynchronous merge REST API`, and `--auto` with `Auto-merge is not supported for stacked pull requests`): the legacy merge cannot merge or enqueue it, so auto-merge is not the path. Enqueue the whole stack with one call on its top PR, once every layer's required checks are green and no layer is a draft (otherwise it is refused, nothing merges): `gh stack merge <top> --yes`, or `gh api -X PUT repos/{owner}/{repo}/pulls/<n>/merge-async -H 'X-GitHub-Api-Version: 2026-03-10' -f merge_action=merge_queue -f sha=<head>` (no queue: `-f merge_action=default -f merge_method=squash`), then poll `gh api repos/{owner}/{repo}/pulls/<top>/merge-async/<uuid>` until `status` is `merged`, `enqueued` (queued, not merged: wait on the PR) or `failed`. Each layer is its own queue entry and lands as its own squash commit; `gh stack merge <pr-k> --yes` lands layers 1..k and GitHub rebases the rest server-side (update a local copy with `git fetch` and `git checkout -B <branch> origin/<branch>`). Details in `github-pull-requests` (Stacked PRs).
4. **Merge without bypassing** through the forge's auto-merge (`gh pr merge --auto --squash --match-head-commit <sha>`, with `<sha>` the head the verdict names or the script proved: gh arms only when the head is that SHA; `glab mr merge --auto-merge --squash`, `az repos pr update --auto-complete true --squash true`), or enqueue when a merge queue exists. Never use `--admin`, `--bypass-policy` or disable a rule. Never push to an armed or queued PR (`github-pull-requests`, Landing a change, rule 9): disarm, push, re-verify, re-arm.
   **Auto-merge unavailable** (GitHub only; for example a private repo on the Free plan): when the forge reports it (`gh api repos/{owner}/{repo} --jq .allow_auto_merge` prints `false`, or arming fails with `Auto merge is not allowed for this repository`) and the repo has no merge queue (a queue gives the same error; enqueue instead), merge directly once `gh pr checks <n> --watch` exits 0 with every check passed: `gh pr merge <n> --squash --match-head-commit <sha>`, with the head SHA the checks ran on. Never enable the repo setting or add `--admin` to get there; if the plain merge is refused, stop and report why.
5. **Wait until it ends, however it ends**, never on merged alone: a failed required check leaves an armed PR open for good, and a loop on its state never returns. On GitHub run `${CLAUDE_PLUGIN_ROOT}/skills/land/scripts/wait-pr.sh <n>` (unrendered: `scripts/` under the path this skill was loaded from; `.ps1` on Windows; exits and options in its header): it returns on merged, closed, a failed required check, a branch behind or in conflict, or its timeout. Its `--timeout` is the deadline in the background, never the tool's (see `subagent-orchestration`, Waiting on other agents). On any exit but merged, act on what it printed (step 1, update the branch as `github-pull-requests` rule 5 allows: `DIRTY` is a conflict, `BEHIND` a required up-to-date branch without a queue, or report); once merged, `git pull --ff-only` on the default branch.
6. **Clean up:** once the PR shows merged, remove this task's worktree (`git worktree remove <path>`, never `--force`; if it refuses, report `git -C <path> status --short` and stop), delete the local branch (`git branch -D <branch>`: the guard lets it through, since the merged PR holds its tip) and `git worktree prune`, each as its own command, never chained after `gh pr merge` (the guard checks the delete against the merged PR before the command runs). The forge deletes the remote branch on merge. A PR closed without merging keeps its remote branch until the sweep removes it after 7 idle days (`github-pull-requests`, Branch lifecycle).
   After the merge, an issue the PR fixed is closed; if no closing keyword did it, comment with the PR link and close it (`github-pull-requests`, Branch lifecycle).
7. **Verify where it lands.** Merged is not working: wait for whatever the merge triggers, then prove the change took effect with one check that reads the real target, not the repo. For example:
   - a deployed service: the deploy or release run finished green, then its health endpoint or service status;
   - dotfiles: `chezmoi diff` is empty after apply, and the changed line is in the rendered file;
   - a plugin or extension: the marketplace or package update ran, and the installed version is the new one;
   - a library: the release and tag exist with the new version.
   When the check needs access you lack or a step the user runs, say so and give the exact command.

Report the merge commit, the verify evidence (command and result) or what was skipped and why, and anything left behind.
