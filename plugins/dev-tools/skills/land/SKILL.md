# Land

Take an open PR (GitLab: MR) to merged and clean. Argument: a PR number; default is the current branch's PR. Detect the forge and take its commands from the `repo-standard` mapping; on GitHub also follow `github-workflow`. The argument is the text after the skill name, repeated here when the harness fills it in: $ARGUMENTS

1. **Watch CI** (GitHub `gh pr checks --watch`, GitLab `glab ci status --live`, Azure DevOps `az repos pr policy list`). On failure, fix lint or format problems with a new commit and push; for anything else, stop and report the failing job and its log.
2. **Merge only when every check passed.** Never merge on a failing or missing check, even if branch protection would not stop you; a red check on `main` is fixed first, in its own PR.
   **Commits after approval:** compare the PR/MR head with the head the reviewer approved. Each commit added since gets a hub check before landing: read its diff and confirm it is what was announced. A pure `git merge` of the base is verified mechanically: `git diff <base> <head>` has the same `git patch-id --stable` as `git diff <old-base> <approved-head>`. Anything with logic beyond picking sides goes back to review.
   **Landing note:** before merging, comment on the PR/MR with the approved SHA, the head being merged, and what was checked for each post-approval commit, so the history records why an unreviewed commit was acceptable.
   **Merge helpers:** never push from an author's worktree, which may hold unpushed, unreviewed commits. Sync a PR/MR branch from a fresh detached worktree at the pushed head, and check the result's first parent is that head before pushing.
3. **Retarget stacked children first.** Before arming the merge, list PRs based on this branch (`gh pr list --base <branch>`, `glab mr list --target-branch <branch>`, `az repos pr list --target-branch <branch>`) and retarget each to the default branch, with its auto-merge off until this PR merges: deleting this branch on merge can close a child whose base disappears. After the squash, merge the default branch into each child before landing it; the steps, and the recovery for a child already closed, are in `github-workflow` (Stacks without `gh stack`).
4. **Merge without bypassing** through the forge's auto-merge (`gh pr merge --auto --squash`, `glab mr merge --auto-merge --squash`, `az repos pr update --auto-complete true --squash true`), or enqueue when a merge queue exists. Never use `--admin`, `--bypass-policy` or disable a rule.
   **Auto-merge unavailable** (GitHub only; for example a private repo on the Free plan): when the forge reports it (`gh repo view --json autoMergeAllowed` is `false`, or arming fails with `Auto merge is not allowed for this repository`) and the repo has no merge queue (a queue gives the same error; enqueue instead), merge directly once `gh pr checks <n> --watch` exits 0 with every check passed: `gh pr merge <n> --squash --match-head-commit <sha>`, with the head SHA the checks ran on. Never enable the repo setting or add `--admin` to get there; if the plain merge is refused, stop and report why.
5. **Wait until it ends, however it ends**, never on merged alone: a failed required check leaves an armed PR open for good, and a loop on its state never returns. On GitHub run `${CLAUDE_PLUGIN_ROOT}/skills/land/scripts/wait-pr.sh <n>` (`.ps1` on Windows; exits and options in its header): it returns on merged, closed, a failed required check, a branch behind or in conflict, or its timeout. Its `--timeout` is the deadline in the background, never the tool's (see `subagent-orchestration`, Waiting on other agents). On any exit but merged, act on what it printed (step 1, update the branch, or report); once merged, `git pull --ff-only` on the default branch.
6. **Clean up:** `git worktree remove <path>` for this task's worktree, never `--force`; if it refuses, report what is left in the worktree (`git -C <path> status --short`) and stop. Then delete the local branch and `git worktree prune`. Run each as its own command once the PR shows merged, never chained after `gh pr merge` or in one long chain: a guard checks a branch delete against the merged PR before the command runs, so in the same chain as the merge it finds none and asks, and it denies a risky step buried in a chain of more than 3 commands.
   A PR closed without merging keeps its remote branch (GitHub deletes only on merge): delete it (`git push origin --delete <branch>`) once no child is based on it.
7. **Verify where it lands.** Merged is not working: wait for whatever the merge triggers, then prove the change took effect with one check that reads the real target, not the repo. For example:
   - a deployed service: the deploy or release run finished green, then its health endpoint or service status;
   - dotfiles: `chezmoi diff` is empty after apply, and the changed line is in the rendered file;
   - a plugin or extension: the marketplace or package update ran, and the installed version is the new one;
   - a library: the release and tag exist with the new version.
   When the check needs access you lack or a step the user runs, say so and give the exact command.

Report the merge commit, the verify evidence (command and result) or what was skipped and why, and anything left behind.
