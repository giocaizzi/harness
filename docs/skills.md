# Writing skills

The skills and agents here follow two posts: [The new rules of context engineering for Claude 5 generation models](https://claude.dev/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models/) (Thariq Shihipar, July 2026) and [Lessons from building Claude Code: How we use skills](https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/) (June 2026). The spec a `SKILL.md` must pass is [agentskills.io](https://agentskills.io/specification), checked by `make validate`.

## Rules

- **A guide, not a rulebook.** A skill helps the agent find what it needs and leaves the rest to its judgement. Keep hard rules for the places where a mistake is costly.
- **Opinions only.** Write down what is particular to us (conventions, choices, gotchas). Leave out what the model already knows or can read from the repo.
- **A published style guide is a baseline, not content.** A language skill names its baseline once (the Google style guides for Go, Python and TypeScript) and writes only what adds to it: stricter rules, choices the guide leaves open, and the tooling that enforces it. A rule that contradicts the baseline is a bug; a guide rule a linter can check is switched on in the skill's shipped config, and the rest are listed as review-only.
- **No conflicting instructions.** Two rules that pull in different directions cost more than either one is worth. Before adding a rule, check that no other skill or `AGENTS.md` contradicts it.
- **Interfaces over examples.** Examples narrow what the agent tries. Make the scripts, make targets and parameters a skill points to expressive enough that no worked example is needed.
- **Progressive disclosure.** Keep `SKILL.md` short and move detail to `references/` or `scripts/`, which the agent loads only when it needs them. A separate step, such as verification or review, gets its own skill.
- **Say a thing once.** Usage instructions go in one place, such as the script or the skill description, and are not repeated elsewhere.
- **Self-contained.** An installed skill ships without this repo's `docs/`, so no skill file points at them: what the skill needs to act goes in its `references/`, and a pointer that is only further reading is an absolute `https://github.com/giocaizzi/harness/blob/main/docs/...` link (`make validate` checks it).
- **Rich references.** Point to code, tests or a rubric instead of describing them in prose.
- **A description is a trigger.** Write a skill's `description` for the model, saying when to load it, early enough to fire before the work starts: name the files it governs (`.gitlab-ci.yml`, `Dockerfile`), the commands, and the user's own words for the problem ("slow", "flaky", "stuck"), not only the topic. The model picks a skill from its description alone, so guidance filed under another skill's description is never loaded for that work. **At most 250 characters, "Use when ..." first** (`make validate` fails longer ones): Claude Code lists every skill by name and description within a budget of 1% of the context window by default, drops the descriptions of the least-used skills first when it overflows, and cuts each at 1,536 characters ([skill descriptions are cut short](https://code.claude.com/docs/en/skills.md#skill-descriptions-are-cut-short)), so a long description loses the very words that make the model pick the skill. Keep what the skill covers in its body, which the model reads once the skill is loaded. A skill the model still under-picks gets a guard `files` or `remind` rule on its files and commands. An agent's `description` is its interface: when to use it, when not, and what not to pass.
- **One of nine categories.** A skill is exactly one of: library and API reference; product verification; data fetching and analysis; business process and team automation; code scaffolding and templates; code quality and review; CI/CD and deployment; runbooks; infrastructure operations. Name it in the PR body. A skill that mixes categories confuses the agent: split it, or move the other parts to `references/`.
- **Technique skill, platform skills.** Techniques that hold on any platform (CI/CD, containers, testing) live in one technique skill that works alone and triggers on the task wherever it runs; each platform's spelling and gotchas live in that platform's own skill, which names the technique skill instead of repeating it. The technique skill names its platform skills, and carries the platforms without one as a mapping table in `references/`. Examples: `ci-cd` (techniques; GitLab, Azure Pipelines and Jenkins in its references), `github-actions` (the GitHub spelling), `github-pull-requests` (landing PRs, another category); `releases` (what gets a version and how it ships, on any stack), `release-please` (the house tool), `semver` (the number).
- **Setup.** A skill that needs per-user values (a channel, a project id) keeps them in `config.json` under `${CLAUDE_PLUGIN_DATA}/<skill>/`, not in the skill folder: the plugin cache is replaced on every version change. When the file is missing, the script prints `NOT_CONFIGURED`, the agent asks with the harness's question tool and saves the answer. Where `CLAUDE_PLUGIN_DATA` is unset (VS Code), fall back to `~/.local/state/giocaizzi-harness/<skill>/`.
- **Memory.** An append-only log (`<skill>.log`, JSONL) in the same directory lets a skill say what changed since its last run. Never store secrets or private values there.
- **On-demand hooks.** Claude Code supports skill-scoped hooks, but other harnesses do not. Behaviour that applies "while skill X is loaded" is a guard rule keyed to loaded skills (guard already tracks them), so every harness gets it. A guard rule that points at a skill from another plugin is a `remind`, never a deny: the plugin may be absent on that machine.
- **Measuring.** `make agent-review` (or `/agent-review` in a session) reports skills never loaded and never picked by the model. A skill stays 30 days before pruning. A row where the model never picks the skill gets a trigger eval (see Evals below).
- **Try simplifying.** Before adding a rule, try deleting one. Re-read a skill after each model generation and prune obsolete gotchas. In Claude Code, `/doctor` checks skills and instruction files against these practices.
- **Gotchas.** Failure points go in a skill's `## Gotchas` section, one line per real failure, pruned once a model change makes a line obsolete: they are the highest-signal part of a skill.
- **Goals over scripts.** State the goal and the constraints; don't railroad steps the agent can order itself.

## Evals

Each skill that should fire without being named gets at least one positive case, each in `plugins/<plugin>/evals/<skill>-trigger/` or `<skill>-<situation>/` (for example `react-effect-loop/`): `case.yaml` (tag `trigger`, a realistic prompt that does not name the skill), `scaffold.sh` (a tiny git repo built in a throwaway dir) and `graders/skill-fired.md` (`tool_used: Skill` matching the skill). A case that does not fire is a gap in the skill description: improve the prompt once, then open an issue for the description rather than dropping the case.

A skill added or re-evaluated from now on gets at least two positive cases and a negative case, `plugins/<plugin>/evals/<skill>-negative/`: a nearby prompt it must stay quiet on, graded by the same `tool_used: Skill` grader with `min: 0` and `max: 0`. The count includes only calls matching `input_match`, so another skill firing does not fail it.

A skill step that must hold in a given state gets a behavior case beside them, `plugins/<plugin>/evals/<skill>-<step>/` with tag `behavior`: the scaffold also writes the state the step reads (for example a ticket snapshot), and an `llm` grader lists what the answer must do.

Routing cases (tag `routing`, `plugins/dev-tools/evals/routing-*`) check that the hub hands each kind of work to the right agent: a plan, a design, an investigation, a root-cause fix and a feature to `driver`, a cross-module lookup to `scout`, a fully specified edit never to `driver`, and a one-line question to no agent at all. Each grades the `Agent` call's `subagent_type`. Five carry `routing-dev`, the cases a description change is tuned on; the other four carry `routing-holdout` and are only measured, so a change that overfits the tuning cases shows. Run them on each session model a hub may use, with the tools a real session has: `make eval PLUGIN=dev-tools TAG=routing MODEL=sonnet ALLOW="Write Edit Bash"`, then `MODEL=opus`. An eval run loads only the plugin under test, never a `CLAUDE.md` (not even one a scaffold writes), so these cases measure the plugin alone; to measure a line of global instructions on top, copy the cases into another eval directory below the plugin with the line as `execution.append_system_prompt` (`schema_version: "1.1"`) and pass `--eval-dir`. `driver-open-question` (tag `behavior`) checks that the driver returns the user's decisions as open questions. The routing-shape cases (tag `routing-shape`, also `routing` with `routing-dev` or `routing-holdout`) check how the work is split and raised: an approved plan of file-disjoint units goes to one `worker` per unit (`routing-batch`, at least three or four spawns), a feature handed to the driver comes back with workers the driver spawned itself (`routing-fanout`, graded on a worker spawn that carries a subagent's `parent_tool_use_id` in the trace: an eval trace records the driver's own tool calls, not its workers'), a sensitive review spawns `reviewer` with `model: opus` and `effort: high` (`routing-review-safety`: an auth change, and a large refactor of a core process), and a routine review spawns it with neither (`routing-review-routine`). Run them with `claude plugin eval plugins/dev-tools --tag routing-shape --ablation none --scaffold --trust-plugin --no-publish --model sonnet --allow-tools Bash Write Edit --max-cost-usd <usd>`; the fanout cases run an Opus driver and cost the most.

`make eval [PLUGIN=<plugin>] [TAG=trigger] [MODEL=<model>] [RUNS=<n>] [ALLOW=<tools>] [MAX_COST=<usd>] [CASE=<glob>] [J=<n>]` runs them with `claude plugin eval <plugin> --tag <TAG> --ablation none --scaffold --trust-plugin --no-publish --keep-temp` (`--model`, `--runs`, `--allow-tools` when set), for every plugin with an `evals/` directory or for one. Run it by hand: it calls a model (about $0.15 per run, 3 runs per case) and is not part of `make check` or CI. Results land in `plugins/<plugin>/evals/results/` (git-ignored); `--no-publish` keeps the HTML report local. Without `--allow-tools`, `claude plugin eval` withholds `Edit` and `Write` ("not granted") even when a case lists them, and which skills fire then changes. So `make eval` grants, unless `ALLOW` is given, the tools that the selected cases (`TAG`) declare in `execution.allowed_tools` and that need a grant: every one except `Read`, `Glob`, `Grep` and `Skill`, and `Bash` only when a case declares it. To run one case or a few by hand, call `claude plugin eval` with `--case <glob>`: it takes a single glob, and braces do not expand (`--case 'ci-cd-*'`, not `--case '{ci-cd,releases}-*'`).

Scores are kept in git so runs can be compared instead of re-run: `plugins/<plugin>/evals/scores.jsonl` is append-only, one JSON line per case per eval run, with `run` (the results dir), `date` (the run's start, UTC), `commit` (the tree evaluated), `dirty` (whether tracked files under the plugin, other than `evals/results/` and the scoreboard, had uncommitted changes when the row was recorded; left out when unknown), `harness` and `harnessVersion`, `model` (the exact id), `plugin` and `pluginVersion`, `case`, `tags`, `allow` (the tools granted with `--allow-tools`, sorted; empty when none; left out of the first rows, recorded before the field), `passes`, `passRate`, `score`, `costUsd` (judge included) and `runs`, every execution's `passed`, `score`, `turns`, `durationSeconds`, `costUsd` and `error`. `make eval` appends the rows of each run it starts, at the `HEAD` commit; commit the file with the change it measures. The model is always an exact id (`claude-opus-5-5`, never an alias such as `sonnet`): the one the run's trace names (its `system`/`init` line), else `MODEL` when it is an exact id; otherwise recording fails rather than guess. `claude plugin eval` deletes its temp dirs, traces included, unless given `--keep-temp`, so `make eval` passes it and the recorder deletes those kept dirs once it has read them (a kept dir is sealed read-only, so the recorder makes it writable first; a dir it cannot remove only warns). `make eval KEEP_TEMP=1` records as usual but keeps those dirs and prints each run's `out/trace.jsonl` (made readable, `sealed/` untouched), so a recorded run can be read with `jq` to see, for example, which skill fired instead; remove them afterwards with `make eval-clean-temp`. `make eval-clean-temp` removes the `e-*` kept dirs that earlier runs left in the temp dir, `/tmp` included; do not run it while an eval is running. To record results by hand, for example from another worktree or after the traces in the temp dir are gone: `make eval-record PLUGIN=<plugin> DIRS="<results dir>..." COMMIT=<sha the run evaluated> MODEL=<exact model id> [DIRTY=true|false] [ALLOW="<granted tools>"]` (without `DIRS`, every dir under `evals/results/`). A row already there (same `run` and `case`) is skipped, so recording twice is harmless. `make eval-scores [PLUGIN=<plugin>]` prints the latest row per case; for anything else, `jq` over the file or `git log -p` on it.
