# Compatibility

What each plugin does under each harness, why, and how it is checked. Install steps: [install.md](install.md). Hook details: [guard.md](guard.md), [hud.md](hud.md), [sounds.md](sounds.md).

Versions checked: Claude Code 2.1.296, Copilot CLI 1.0.95, VS Code 1.139, Codex CLI 0.162.1, opencode 1.19.0, pi 1.2.0 (October 2026).

Hosts: everything runs on macOS, Linux and Windows; the hooks need `node` 22+ on PATH. CI drives Codex, opencode and pi on all three ([Verify](#verify)); Claude Code, Copilot CLI and VS Code are checked live on macOS only, Windows is pending ([#25](https://github.com/giocaizzi/harness/issues/25)).

**Parity rule:** every skill and agent reaches every harness above. `make validate` enforces it through `scripts/parity.mjs`, which reads each harness's delivery from what that harness consumes: the marketplace and the Claude, Copilot and Codex plugin manifests, the plan of `scripts/install.mjs` (Codex agents, opencode) and `package.json`'s `pi` key plus the agents the `subagent` tool loads. VS Code reads the Claude format, so the Claude delivery covers it. It also fails on a skill name used by two plugins, since opencode and pi install skills by name, and on an agent whose tier differs between harnesses: only Claude names the model, the Codex, Copilot and opencode files pin none (they take the session's), and the Claude `effort` equals Codex's `model_reasoning_effort`. A row above that says "no" is a hook or UI feature, never a skill or agent.

## User-level setup

What a harness reads from the user's home rather than from a plugin. This repo ships none of it; a dotfiles repo renders it per machine. Paths are the defaults (`$CODEX_HOME`, `$XDG_CONFIG_HOME`, `$PI_CODING_AGENT_DIR` move them).

| | Claude Code | Copilot CLI | VS Code Copilot | Codex CLI | opencode | pi |
|---|---|---|---|---|---|---|
| Global instructions | `~/.claude/CLAUDE.md` | `~/.copilot/copilot-instructions.md` (`copilot instruction list` shows it) | user `*.instructions.md` files in the profile (unverified) | `~/.codex/AGENTS.md` | `~/.config/opencode/AGENTS.md` | `~/.pi/agent/AGENTS.md` |
| Private instructions (a second file kept out of the shared one) | imported from the global file with `@<path>` | no import: inlined into the global file | a second `*.instructions.md` | no import: inlined | inlined, or listed in `instructions` of `opencode.json` | no import: inlined |
| User MCP servers ([details](#mcp-servers)) | `~/.claude.json` | `~/.copilot/mcp-config.json` | profile `mcp.json` | `~/.codex/config.toml` | `~/.config/opencode/opencode.json` | `~/.pi/agent/mcp.json` |
| Invoke a skill | `/<plugin>:<skill>`, `Skill` tool | `/<skill>`, `skill` tool | `skill` tool | `$<plugin>:<skill>` (a bare `$<skill>` loads nothing) | `/<skill>`, `skill` tool | `/skill:<name>` |

The global instructions are one `AGENTS.md`, rendered per machine role and placed (or linked) at each harness's path above; the private part lives outside the public dotfiles and is imported where the harness can, inlined where it cannot.

Machine roles:

- **Full, personal (macOS):** every harness above, every plugin.
- **Full, work (Windows):** the harnesses that machine selects, the same plugins; the hooks need `node` 22+ there too.
- **Light (Linux, Raspberry Pi):** harness-free on purpose: no harness config, instructions or plugins, and agents never run there, so nothing in this repo targets it. Linux stays supported for other machines and CI.

## MCP servers

Where each harness reads MCP servers, for the `repo-standard` rule (repo servers committed per harness, user scope minimal). Checked on the versions above, Copilot CLI 1.0.96.

| Harness | Project file (committed), key | User file | Private per-repo | Remote OAuth login | Secrets in config | Variable in a URL |
|---|---|---|---|---|---|---|
| Claude Code | `.mcp.json`, `mcpServers` (approved once) | `~/.claude.json` `mcpServers` | yes: `claude mcp add -s local` | `/mcp` or `claude mcp login <name>`; not in `claude -p` | `${VAR}`, `${VAR:-default}` | yes, `${VAR}` |
| Copilot CLI | `.mcp.json` or `.github/mcp.json` (`.mcp.json` wins), `mcpServers`; trusted folders | `~/.copilot/mcp-config.json` | no: a gitignored `.mcp.json` | not documented: static headers only | not documented: literal `env` only | yes, `${VAR}` (undocumented, checked) |
| VS Code Copilot | `.vscode/mcp.json`, `servers` (also reads `.mcp.json`, experimental) | profile `mcp.json` | no | `oauth` object on the server; browser on first connect | `${input:id}` (`inputs`), `envFile` | unverified |
| Codex CLI | `.codex/config.toml`, `[mcp_servers.<name>]`; trusted projects | `~/.codex/config.toml` | no: `-c mcp_servers.…` overrides | `codex mcp login <name>` (default for streamable HTTP) | named references: `env_vars`, `bearer_token_env_var`, `env_http_headers` | no (checked) |
| opencode | `opencode.json(c)`, `mcp` (`type: local/remote`, `command` array) | `~/.config/opencode/opencode.json` | no: `OPENCODE_CONFIG_CONTENT` | automatic on 401, `opencode mcp auth <name>` | `{env:VAR}`, `{file:path}` | yes, `{env:VAR}` (checked) |
| pi | `.pi/mcp.json`, `mcpServers`; trusted projects | `~/.pi/agent/mcp.json` | no | `pi mcp login <name>`; no legacy SSE | `${VAR}` in `env`/`headers`, `!command` | no: `env` and `headers` only (checked) |

- **One name, six shapes.** Claude Code, Copilot CLI and pi share the `.mcp.json` shape; VS Code (`servers`), Codex (TOML) and opencode (`mcp`, `type`) differ, and the secret syntax differs everywhere, so each project file is written for its harness with the same server names.
- **Parent folders.** Claude Code merges the `.mcp.json` of every parent folder into the session, inside a git repo too (each still needs its one-time approval), while `.claude/settings*.json` applies only in its own folder (checked on 2.1.296). Copilot CLI searches `.mcp.json` only up to the repo root. So a workspace file never sits in the home directory or above repos.
- **Private URL parts in a public repo.** A repo file can hide an account or host only where the harness expands a variable in the URL: Claude Code, Copilot CLI and opencode (checked with a local listener: the request arrived on the expanded path). Codex and pi send the reference as is, so they get no repo file there; a file rendered outside the repo (user scope, a workspace folder) can carry the value instead.
- **Trust before loading.** Copilot CLI and pi ignore project files in a folder they do not trust yet (`copilot mcp list` and `pi mcp list` show only user servers); Codex the same, unless the folder is trusted in `~/.codex/config.toml` (`[projects."<path>"] trust_level = "trusted"`).
- **Private trial is Claude-only.** The other harnesses have no uncommitted per-repo scope; the nearest is a gitignored project file or a per-run override, as in the table.

## Decisions

- **One engine, thin adapters.** The rules live in `plugins/guard/core/` and `hooks/guard.mjs#handle`. Command-hook harnesses (Claude, Copilot, VS Code, Codex) run `guard.mjs`; in-process ones (opencode, pi) go through `hooks/bridge.mjs`, which builds the same Claude-shaped payload and calls the same handlers. A rule change reaches all six harnesses.
- **Codex reads the Claude plugin, nearly.** Codex resolves `.claude-plugin/marketplace.json`, installs each plugin and discovers its skills, and runs `hooks/hooks.json` with the Claude payload (`tool_name: "Bash"`, `hookSpecificOutput.permissionDecision`) and `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` set. Two things break: it rejects the whole hooks file for the Claude-only `modules` key, and it does not support `ask` (it marks the hook failed and runs the command). So `build_agents.py` writes `hooks/codex.json` without `modules` and with `--no-ask` on the guard, and a `.codex-plugin/plugin.json` that points at it.
- **Codex hooks need trust.** Codex skips plugin hooks until they are trusted in `/hooks`, per hook hash, so each guard version needs one review. `--dangerously-bypass-hook-trust` skips that for one run (the e2e tests use it).
- **No hook ask: the harness's own prompt rules ask** ([#69](https://github.com/giocaizzi/harness/issues/69)). Codex and opencode hooks cannot ask, so each risky rule lists `prefixes` (`core/rules.mjs`) that the harness prompts for itself: Codex execpolicy rules (`prefix_rule(..., decision = "prompt")`, written by `make install HARNESS=codex` to `$CODEX_HOME/rules/giocaizzi-guard.rules`) and opencode `permission.bash` ask entries (`rm -rf *`, ...) that the plugin's `config` hook appends last, so they win over a user's `allow`. When the guard would ask and the command is single-spaced plain words (letters, digits and `./@%+=:,-` only) starting with a prefix, it lets it through to that prompt; anything else is denied with the reason and "ask the user to run it". Plain words matter: Codex consults its prompt rules only for a command it can parse into words, so `rm -r $PWD/x`, `rm -r x*`, `rm -r ~/x` or a quoted or escaped argument ran unasked in review, and the guard denies them. The guard leaves a command to Codex only when the installed rules file is exactly this version's and the session's last `turn_context` in its rollout (the hook's `transcript_path`) has `approvals_reviewer` `"user"`, the effective value whatever set it (config, profile, `-c`, `--approve-for-me`; an AI reviewer could approve the prompt; no record denies); to opencode only when the entries are in, the process is not `opencode run --auto` in any spelling (`--auto=true`; it approves every ask) and the session has no bash rule of its own (an API caller's `tools: { bash: true }`). Non-interactive runs reject: under approval `never` (`codex exec`, `--dangerously-bypass-approvals-and-sandbox`) a Codex prompt rule is a rejection, and `opencode run` auto-rejects a permission request.
- **Known limits of borrowed prompts.** Not visible to the guard: `opencode run --attach <url> --auto` (the approving client is another process; the server's argv lacks the flag); there `--auto` approves a covered plain command. Persistent approvals cover a whole prefix: Codex's "don't ask again" and opencode's "Allow always" can let later commands with the same prefix run unasked. Codex on Windows wraps commands in PowerShell; whether its prompt rules see them there is untested.
- **Why not the hooks named in #69.** Codex's `PermissionRequest` fires only when Codex was going to prompt anyway (checked on 0.162.1: it fired for a prompt rule, never for a command the sandbox allowed) and answers only `allow` or `deny`; `PreToolUse` `updatedInput` can only rewrite `command`. opencode 1.19.0 declares the `permission.ask` plugin hook but never calls it (`Permission.ask` in `packages/opencode/src/permission/index.ts` publishes the request without a plugin trigger), and `tool.execute.before` gets no `ask`.
- **The cost of borrowed prompts.** The harness matches the prefix, not the guard's rules, so it also prompts for a safe temp delete and shows no blast-radius preview. A user `deny` on opencode's `bash` (or `*`) skips the entries entirely, so it is never weakened, and the guard denies as before.
- **opencode has no plugin bundles.** Its plugins are npm packages or local files, and it has no marketplace, so `scripts/install.mjs` copies the skills and agents and writes a one-line plugin stub that re-exports `hooks/opencode.mjs` from the checkout. A pull updates the hook code; re-run the installer for skills and agents.
- **pi installs the repo.** `pi install git:github.com/giocaizzi/harness` reads the root `package.json`: `pi.skills` loads every plugin's skills, `pi.extensions` the guard, the subagent tool, hud's footer and sounds' alerts.
- **pi subagents are a tool.** pi has no subagents by design; `dev-tools/pi/subagent.mjs` registers `subagent` (`agent`, `task`), which runs the agent in its own `pi -p --no-session` process with its prompt appended (`--append-system-prompt`), its Claude `tools` mapped to pi's (`--tools`; scout: read, grep, find, ls, bash) and the session's model, and returns the final text. Agents come from the Claude-format `agents/*.md`, so nothing else is generated.
- **Codex and opencode get sounds, not hud.** Codex's `Stop` hook names the turn and its rollout, which holds the start time, errors and token counts, so `sounds/hooks/codex.mjs` plays the turn and context clips and returns the notices as `systemMessage` (a warning line); it lives in `hooks/codex-only.json` so the other command-hook harnesses do not run it. opencode's `session.idle`, `session.error` and `message.updated` events and `client.tui.showToast` carry the same alerts in `sounds/hooks/opencode.mjs`. Neither has a status-line command or a documented UI slot for `hud`. Codex's `token_count` events also carry `rate_limits`, so limit alerts and the throttle may be possible there ([#68](https://github.com/giocaizzi/harness/issues/68)).
- **pi gets hud and sounds from its UI API.** The footer status (`ctx.ui.setStatus`) carries the context weather, the model and the PR strip, refreshed after each run; `ctx.ui.notify` and `afplay` carry the turn and context alerts. pi has no per-plugin settings, no plan rate-limit windows and no prompt-cache TTL, so the clips are the Claude defaults and the limit and cache alerts are left out.
- **Reply rewrites: only Claude Code and pi can rewrite what a reply shows** ([#82](https://github.com/giocaizzi/harness/issues/82); details in [hud.md](hud.md#reply-rewrites)). Claude Code's mod `ui.render` hook on `AssistantMessage` rewrites the drawing and leaves the stored message alone; colour needs a tree of the hook's own, since markdown carries none and a rewritten reply may not hold escape sequences. pi's `message_end` replaces the finished message (pi-tui draws a markdown link as an OSC 8 hyperlink showing only its label, any scheme); colour is not possible there, as pi's markdown takes none and an escape sequence would be stored and sent to the model. pi has no per-plugin settings, so hud reads `hud.json` in its config directory.
  - Copilot CLI 1.0.96: its hooks can only change a tool result (`postToolUse` `modifiedResult`).
  - VS Code: its hooks can only change tool permission and input, add context or block a stop.
  - Codex 0.162.1: its hooks can only change tool input or MCP output, or add a `systemMessage`.
  - opencode 1.19.0: `experimental.text.complete` rewrites a completed text part (a prototype worked). But OpenTUI's markdown renderer draws a link as `label (url)` in conceal mode, and `[label](url)` without it, so the URL always shows; the rewrite is also stored. Not shipped.
- **Stop in-process.** opencode and pi have no stop hook that blocks; the guard runs `make check` when the session goes idle or the run settles and, on failure, sends the output back as a new message once. The check runs synchronously, so the harness waits for it as a command hook would.
- **Agents' models.** The shared `model` names a Claude tier, so Codex and opencode agents get none and inherit the session's model; `src/agents/<name>/codex.yaml` and `opencode.yaml` add harness-only keys (scout: read-only sandbox, edit denied).
- **Decision log env.** Claude Code and Copilot CLI strip `OTEL_*` from a command hook's environment (checked on Claude Code 2.1.296 and Copilot CLI 1.0.96: a hook sees `TRACEPARENT` but no `OTEL_EXPORTER_OTLP_*`, while other variables pass), so the guard falls back to `GUARD_OTEL_EXPORTER_OTLP_ENDPOINT`, `GUARD_OTEL_EXPORTER_OTLP_HEADERS` and `GUARD_OTEL_RESOURCE_ATTRIBUTES`, which the launching shell exports (the dotfiles render them from the secrets file). The Claude mod reads `OTEL_*` in-process and needs no copy.
- **Copilot CLI session settings.** No prompt-cache TTL or auto-compact window exists (`copilot help config`, `copilot help environment`, 1.0.96); the only context knob is `contextTier`. Per-subagent `model` and `effortLevel` do exist, user settings only: `subagents.agents.<plugin>:<agent>` (e.g. `dev-tools:scout`), not settable with `copilot config` or in repo settings. A configured model the account lacks falls back to an available one (`configuredModelMatchesActual: false` in the `subagent.completed` event).
- **No suggested follow-up prompts outside Claude.** Claude Code gets them from `next-steps@claude-community` (a mod: a model fork after each turn, buttons above the prompt, `$.prompt.fill`). Copilot CLI hooks can only add context or decide on tool calls, and its extensions (`~/.copilot/extensions`, not shippable in a Claude-format plugin) can log to the timeline but cannot fill or suggest input: `prefillInput` exists only on built-in slash-command results, an extension command handler returns nothing. VS Code offers follow-ups only to chat participants of a VS Code extension. Codex hooks cannot touch the composer. opencode (`client.tui.appendPrompt`) and pi (`ctx.ui.setWidget`, `ctx.ui.setEditorText`, `agent_end`) have the primitives, but nothing is built yet ([#28](https://github.com/giocaizzi/harness/issues/28)).
- **Skill arguments in words.** Claude Code and opencode replace `$ARGUMENTS` in a skill invoked with an argument; Codex 0.163.0 and pi 1.3.0 leave it as is and carry the argument in the message (pi appends it after the skill block), and Copilot CLI 1.0.98 has no placeholder handling. So each skill that takes one says ``Argument (`$ARGUMENTS`, or the text after the skill name where that placeholder is left as is)``, which reads right either way. `make e2e` invokes `wt` with an argument on Codex, opencode and pi and checks the body and the argument reach the model, and whether `$ARGUMENTS` was replaced.
- **No root `plugin.json`.** The Agent Plugins spec's root `plugin.json` would win Copilot's and VS Code's manifest lookup, so the repo keeps per-harness manifests instead.

```bash
make check   # validate (incl. `claude plugin validate` and the parity check) + node tests + `claude plugin test`
make e2e     # Codex, opencode and pi against a scripted model (tests/e2e), each in a throwaway home
```

`make e2e` needs the three CLIs on `PATH` ([install runbook](install.md#verify), no global install needed) but no login: `tests/e2e/mock-llm.mjs` speaks the Responses and Chat Completions APIs and scripts one shell call. For each harness it installs this checkout the documented way, then checks that a `pip install` in a uv project is denied with the guard's reason, that a plain risky command (`git reset --hard`) reaches the harness's own prompt, rejected in a non-interactive run (pi: blocked without a UI), that a compound one (`cd . && rm -rf ~/…`) is denied, and that every skill and agent in the repo is in the model's prompt (Codex installs every marketplace plugin for this); on Codex it also checks that sounds' `Stop` hook ran; on pi it also delegates to `scout` through the `subagent` tool and checks the child session ran. CI runs it on Linux, macOS and Windows (`e2e` job).

### With a real model

Run the same two prompts by hand on an installed harness, from a uv project (a directory with `pyproject.toml` and `uv.lock`; outside one the pip rule does not fire):

```bash
copilot -p "Run exactly this shell command: pip install requests" --allow-tool shell
opencode run -m opencode/nemotron-3-ultra-free "Run exactly this shell command with the bash tool: pip install requests"
# then the same with: rm -rf ~/harness-e2e-does-not-exist
```

Expected: the pip call is denied with "This repo uses uv", and the `rm` is not run: Copilot CLI in `-p` mode cannot ask, so it denies; opencode denies it too (`~` is not a plain word). With `rm -rf build` instead, `opencode run` prints `permission requested: bash (rm -rf build); auto-rejecting`. opencode's free models need no login. Codex (`codex exec`) and pi (`pi -p`) need a logged-in provider. Last run (2026-10-13, macOS): Copilot CLI and opencode passed both, Claude Code denied pip; Codex and pi were not run (no login).

The interactive prompt, against the scripted model, each in a throwaway home (the `install` and provider steps of `tests/e2e/run.mjs`): Codex's TUI (`codex -s workspace-write -a on-request`) asked "Would you like to run the following command? … requires approval: guard: recursive delete" for `rm -rf victim` inside the workspace and ran it on yes; opencode's TUI with `permission.bash: allow` showed "Permission required · $ rm -rf victim" and left the directory on Reject (2026-10-13, macOS, Codex 0.162.1, opencode 1.19.0).
