# Compatibility

What each plugin does under each harness, why, and how it is checked. Install steps: [install.md](install.md). Hook details: [guard.md](guard.md), [hud.md](hud.md), [sounds.md](sounds.md).

Versions checked: Claude Code 2.1.296, Copilot CLI 1.0.95, VS Code 1.139, Codex CLI 0.162.1, opencode 1.19.0, pi 1.2.0 (October 2026).

|---|---|---|---|---|

| Codex CLI | same (Codex reads the Claude marketplace) | `.codex-plugin/plugin.json` (generated; wins over `.claude-plugin/`) | `codex/*.toml`, copied by `scripts/install.mjs` (Codex plugins carry no agents) | `hooks/codex.json` (generated: `hooks.json` without `modules`, plus `hooks/codex-only.json`), named by the Codex manifest |
| opencode | none: no plugin bundles | none | `opencode/*.md`, copied by `scripts/install.mjs` | `guard` and `sounds` `hooks/opencode.mjs`, in-process plugins; `install.mjs` writes a stub per plugin into `~/.config/opencode/plugins/` that re-exports it |
| pi | none: packages | root `package.json` (`pi` key) | `agents/*.md` read at runtime by `dev-tools/pi/subagent.mjs` | `guard`, `hud`, `sounds` `hooks/pi.mjs` and `dev-tools/pi/subagent.mjs`, in-process extensions listed in `package.json` |

## Decisions

- **One engine, thin adapters.** The rules live in `plugins/guard/core/` and `hooks/guard.mjs#handle`. Command-hook harnesses (Claude, Copilot, VS Code, Codex) run `guard.mjs`; in-process ones (opencode, pi) go through `hooks/bridge.mjs`, which builds the same Claude-shaped payload and calls the same handlers. A rule change reaches all six harnesses.
- **Codex reads the Claude plugin, nearly.** Codex resolves `.claude-plugin/marketplace.json`, installs each plugin and discovers its skills, and runs `hooks/hooks.json` with the Claude payload (`tool_name: "Bash"`, `hookSpecificOutput.permissionDecision`) and `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` set. Two things break: it rejects the whole hooks file for the Claude-only `modules` key, and it does not support `ask` (it marks the hook failed and runs the command). So `build_agents.py` writes `hooks/codex.json` without `modules` and with `--no-ask` on the guard, and a `.codex-plugin/plugin.json` that points at it.
- **Codex hooks need trust.** Codex skips plugin hooks until they are trusted in `/hooks`, per hook hash, so each guard version needs one review. `--dangerously-bypass-hook-trust` skips that for one run (the e2e tests use it).
- **No hook ask: the harness's own prompt rules ask** ([#69](https://github.com/giocaizzi/harness/issues/69)). Codex and opencode hooks cannot ask, so each risky rule lists `prefixes` (`core/rules.mjs`) that the harness prompts for itself: Codex execpolicy rules (`prefix_rule(..., decision = "prompt")`, written by `make install HARNESS=codex` to `$CODEX_HOME/rules/giocaizzi-guard.rules`) and opencode `permission.bash` ask entries (`rm -rf *`, ...) that the plugin's `config` hook appends last, so they win over a user's `allow`. When the guard would ask and the command is one plain command (no `;`, `&&`, `|`, redirection or `$(...)`) starting with a prefix, it lets it through to that prompt; anything else is denied with the reason and "ask the user to run it". The guard leaves a command to Codex only when the installed rules file is exactly this version's, and to opencode only when the entries are in and the session has no bash rule of its own (an API caller's `tools: { bash: true }`). Non-interactive runs reject: under approval `never` (`codex exec`, `--dangerously-bypass-approvals-and-sandbox`) a Codex prompt rule is a rejection, and `opencode run` auto-rejects a permission request.
- **Why not the hooks named in #69.** Codex's `PermissionRequest` fires only when Codex was going to prompt anyway (checked on 0.162.1: it fired for a prompt rule, never for a command the sandbox allowed) and answers only `allow` or `deny`; `PreToolUse` `updatedInput` can only rewrite `command`. opencode 1.19.0 declares the `permission.ask` plugin hook but never calls it (`Permission.ask` in `packages/opencode/src/permission/index.ts` publishes the request without a plugin trigger), and `tool.execute.before` gets no `ask`.
- **The cost of borrowed prompts.** The harness matches the prefix, not the guard's rules, so it also prompts for a safe temp delete and shows no blast-radius preview. Codex's "always allow" cannot override a prompt rule (the strictest decision wins); opencode's "Allow always" allows that command's prefix (`rm *`) for the rest of the session. A user `deny` on opencode's `bash` (or `*`) skips the entries entirely, so it is never weakened, and the guard denies as before.
- **opencode has no plugin bundles.** Its plugins are npm packages or local files, and it has no marketplace, so `scripts/install.mjs` copies the skills and agents and writes a one-line plugin stub that re-exports `hooks/opencode.mjs` from the checkout. A pull updates the hook code; re-run the installer for skills and agents.
- **pi installs the repo.** `pi install git:github.com/giocaizzi/harness` reads the root `package.json`: `pi.skills` loads every plugin's skills, `pi.extensions` the guard, the subagent tool, hud's footer and sounds' alerts.
- **pi subagents are a tool.** pi has no subagents by design; `dev-tools/pi/subagent.mjs` registers `subagent` (`agent`, `task`), which runs the agent in its own `pi -p --no-session` process with its prompt appended (`--append-system-prompt`), its Claude `tools` mapped to pi's (`--tools`; scout: read, grep, find, ls, bash) and the session's model, and returns the final text. Agents come from the Claude-format `agents/*.md`, so nothing else is generated.
- **Codex and opencode get sounds, not hud.** Codex's `Stop` hook names the turn and its rollout, which holds the start time, errors and token counts, so `sounds/hooks/codex.mjs` plays the turn and context clips and returns the notices as `systemMessage` (a warning line); it lives in `hooks/codex-only.json` so the other command-hook harnesses do not run it. opencode's `session.idle`, `session.error` and `message.updated` events and `client.tui.showToast` carry the same alerts in `sounds/hooks/opencode.mjs`. Neither has a status-line command or a documented UI slot for `hud`. Codex's `token_count` events also carry `rate_limits`, so limit alerts and the throttle may be possible there ([#68](https://github.com/giocaizzi/harness/issues/68)).
- **pi gets hud and sounds from its UI API.** The footer status (`ctx.ui.setStatus`) carries the context weather, the model and the PR strip, refreshed after each run; `ctx.ui.notify` and `afplay` carry the turn and context alerts. pi has no per-plugin settings, no plan rate-limit windows and no prompt-cache TTL, so the clips are the Claude defaults and the limit and cache alerts are left out.
- **Stop in-process.** opencode and pi have no stop hook that blocks; the guard runs `make check` when the session goes idle or the run settles and, on failure, sends the output back as a new message once. The check runs synchronously, so the harness waits for it as a command hook would.
- **Agents' models.** The shared `model` names a Claude tier, so Codex and opencode agents get none and inherit the session's model; `src/agents/<name>/codex.yaml` and `opencode.yaml` add harness-only keys (scout: read-only sandbox, edit denied).
- **Decision log env.** Claude Code and Copilot CLI strip `OTEL_*` from a command hook's environment (checked on Claude Code 2.1.296 and Copilot CLI 1.0.96: a hook sees `TRACEPARENT` but no `OTEL_EXPORTER_OTLP_*`, while other variables pass), so the guard falls back to `GUARD_OTEL_EXPORTER_OTLP_ENDPOINT`, `GUARD_OTEL_EXPORTER_OTLP_HEADERS` and `GUARD_OTEL_RESOURCE_ATTRIBUTES`, which the launching shell exports (the dotfiles render them from the secrets file). The Claude mod reads `OTEL_*` in-process and needs no copy.
- **Copilot CLI session settings.** No prompt-cache TTL or auto-compact window exists (`copilot help config`, `copilot help environment`, 1.0.96); the only context knob is `contextTier`. Per-subagent `model` and `effortLevel` do exist, user settings only: `subagents.agents.<plugin>:<agent>` (e.g. `dev-tools:scout`), not settable with `copilot config` or in repo settings. A configured model the account lacks falls back to an available one (`configuredModelMatchesActual: false` in the `subagent.completed` event).
- **No suggested follow-up prompts outside Claude.** Claude Code gets them from `next-steps@claude-community` (a mod: a model fork after each turn, buttons above the prompt, `$.prompt.fill`). Copilot CLI hooks can only add context or decide on tool calls, and its extensions (`~/.copilot/extensions`, not shippable in a Claude-format plugin) can log to the timeline but cannot fill or suggest input: `prefillInput` exists only on built-in slash-command results, an extension command handler returns nothing. VS Code offers follow-ups only to chat participants of a VS Code extension. Codex hooks cannot touch the composer. opencode (`client.tui.appendPrompt`) and pi (`ctx.ui.setWidget`, `ctx.ui.setEditorText`, `agent_end`) have the primitives, but nothing is built yet ([#28](https://github.com/giocaizzi/harness/issues/28)).
- **No root `plugin.json`.** The Agent Plugins spec's root `plugin.json` would win Copilot's and VS Code's manifest lookup, so the repo keeps per-harness manifests instead.

## Verify

```bash
make check   # validate (incl. `claude plugin validate`) + node tests + `claude plugin test`
make e2e     # Codex, opencode and pi against a scripted model (tests/e2e), each in a throwaway home
```

`make e2e` needs the three CLIs (`npm install -g @openai/codex opencode-ai @earendil-works/pi-coding-agent`) but no login: `tests/e2e/mock-llm.mjs` speaks the Responses and Chat Completions APIs and scripts one shell call. For each harness it installs this checkout the documented way, then checks that a `pip install` in a uv project is denied with the guard's reason, that a plain risky command (`git reset --hard`) reaches the harness's own prompt, rejected in a non-interactive run (pi: blocked without a UI), that a compound one (`cd . && rm -rf ~/…`) is denied, and that the skills and the `scout` agent are in the model's prompt; on Codex it also checks that sounds' `Stop` hook ran; on pi it also delegates to `scout` through the `subagent` tool and checks the child session ran. CI runs it on Linux, macOS and Windows (`e2e` job).

### With a real model

Run the same two prompts by hand on an installed harness, from a uv project (a directory with `pyproject.toml` and `uv.lock`; outside one the pip rule does not fire):

```bash
copilot -p "Run exactly this shell command: pip install requests" --allow-tool shell
opencode run -m opencode/nemotron-3-ultra-free "Run exactly this shell command with the bash tool: pip install requests"
# then the same with: rm -rf ~/harness-e2e-does-not-exist
```

Expected: the pip call is denied with "This repo uses uv", and the `rm` is not run: Copilot CLI in `-p` mode cannot ask, so it denies; `opencode run` prints `permission requested: bash (rm -rf …); auto-rejecting`. opencode's free models need no login. Codex (`codex exec`) and pi (`pi -p`) need a logged-in provider. Last run (2026-10-13, macOS): Copilot CLI and opencode passed both, Claude Code denied pip; Codex and pi were not run (no login).

The interactive prompt, against the scripted model, each in a throwaway home (the `install` and provider steps of `tests/e2e/run.mjs`): Codex's TUI (`codex -s workspace-write -a on-request`) asked "Would you like to run the following command? … requires approval: guard: recursive delete" for `rm -rf victim` inside the workspace and ran it on yes; opencode's TUI with `permission.bash: allow` showed "Permission required · $ rm -rf victim" and left the directory on Reject (2026-10-13, macOS, Codex 0.162.1, opencode 1.19.0).
