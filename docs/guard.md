# guard plugin

Agent rules enforced as hooks, from one plugin, for Claude Code, Copilot CLI, VS Code Copilot (agent plugins), Codex CLI, opencode and pi on macOS, Linux and Windows. What differs per harness: [compatibility.md](compatibility.md).

## Architecture

| Piece | Role |
|---|---|
| `core/rules.mjs` | Data: skill rules (command pattern -> skill), deny rules, heavy and risky command patterns (each risky rule with the `prefixes` Codex and opencode prompt for), title types, host caps, usage thresholds. |
| `core/shell.mjs` | A small shell reader: splits a command into simple commands, blanks quoted text, drops heredoc bodies and comments, and finds payloads that run as code (a shell's `-c`, `eval`, `ssh`'s remote command, `docker`/`kubectl exec`, `cmd /c`, `powershell -Command`, a heredoc or `echo`/`printf` piped into a shell, `$(…)` and backticks), read again three levels deep. |
| `core/engine.mjs` | Pure decisions: `evaluateCommand` (risky ask, title guard, host guard, skill reminder, read and edit hints), `evaluateSpawn`, blast-radius preview argv, safe-delete facts (worktrees, branches, ignored build output) through an injected runner. |
| `core/host.mjs` | Host-fact parsers (load average, free disk, Windows CPU percent). |
| `hooks/hooks.json` | Command hooks, Claude format. Claude Code, Copilot CLI and VS Code load it from the installed plugin. |
| `.generated/codex/hooks.json` | Generated by `make build` for Codex: `hooks.json` without `modules`, the guard run with `--no-ask`. `.codex-plugin/plugin.json` points Codex at it. Its prompt rules (`$CODEX_HOME/rules/giocaizzi-guard.rules`) come from `scripts/install.mjs`, rendered by `codexRules` from the risky rules' `prefixes`. |
| `hooks/bridge.mjs` | The guard for in-process harnesses: turns an event into the Claude-shaped payload and calls the same `handle`, `lintFile`, `stopCheck` and `keepAwake`. |
| `hooks/opencode.mjs` | opencode plugin over the bridge; `scripts/install.mjs` writes a stub in `~/.config/opencode/plugins/` that re-exports it. |
| `hooks/pi.mjs` | pi extension over the bridge, listed in the repo's root `package.json`. |
| `hooks/guard.mjs` | The command guard: reads the event on stdin, gathers facts (host, worktrees, the repo's Python manager), asks the engine, writes `hookSpecificOutput` on stdout. |
| `hooks/stop.mjs` | `make check-fast` (when defined) or `make check` before the agent stops (was the dotfiles `stop-make-check.sh`/`.ps1`). |
| `hooks/lint.mjs` | shellcheck / PSScriptAnalyzer after an edit (was the dotfiles `post-edit-lint.sh`/`.ps1`). |
| `hooks/awake.mjs` | Keep-awake keeper tied to the harness process. |
| `hooks/mod.mjs` | Claude Code mod (`modules` in `hooks.json`, ignored by Copilot CLI and VS Code): the usage throttle and the ask timeout. The UI (band, pane, status line, spinner) is the `hud` plugin ([docs/hud.md](hud.md)); toasts and sounds are the `sounds` plugin ([docs/sounds.md](sounds.md)). |

Events:

| Event (Claude and VS Code / Copilot CLI) | Tools (matcher, re-checked in the script) | What runs |
|---|---|---|
| `SessionStart` / `sessionStart` | all | Keep-awake keeper, one per harness process. |
| `PreToolUse` / `preToolUse` | Shell: `Bash`, `PowerShell` (Claude), `bash`, `powershell` (Copilot), `run_in_terminal` (VS Code). Skill: `Skill`, `skill` | Shell: deny rules (pip, poetry), risky ask, title guard, host guard, skill reminder. Skill: records the loaded skill. |
| `PostToolUse` / `postToolUse` | `Edit`, `Write`, `MultiEdit` (Claude); `edit`, `create`, `Edit` with an apply_patch string (Copilot); `create_file`, `replace_string_in_file`, `multi_replace_string_in_file`, `insert_edit_into_file`, `apply_patch` (VS Code) | Lint the edited files; findings as `additionalContext`. |
| `Stop` / `agentStop` | all | `make check-fast` (when defined) or `make check` when the repo changed since the last green run; on failure `decision: block` once, never when `stop_hook_active`. |
| `UserPromptSubmit` / `userPromptSubmitted` | all | A typed `/skill` counts as loaded. |
| `SessionEnd` / `sessionEnd` | all | Drops state files idle for a week. It keeps the ending session's own: a resumed session keeps its id, and forgetting its loaded skills re-denied every skill rule after each resume. |

Codex runs the same command hooks (`.generated/codex/hooks.json`) with Claude's event names and payload; its shell tool arrives as `Bash`, its edits as `apply_patch`. The in-process harnesses map their own events:

| Guard step | opencode | pi |
|---|---|---|
| Shell guard, skill tracker | `tool.execute.before` (throw denies; ask is opencode's own prompt, from the `bash` ask entries the `config` hook appends) | `tool_call` (`{ block, reason }`; ask is `ctx.ui.confirm`) |
| Post-edit lint, pip note | `tool.execute.after` (appended to the output) | `tool_result` (appended to the content) |
| Typed `/skill` | `chat.message` | `input` |
| `make check` on stop | `session.idle`: on failure `client.session.prompt` once | `agent_settled`: on failure `pi.sendUserMessage` once |
| Keep-awake | `session.created` | `session_start` |
| State cleanup | `session.deleted` | `session_shutdown` |

## Decisions

- **Command hooks, not a mod or an extension.** Copilot CLI (1.0.95) loads a plugin's `hooks/hooks.json`, accepts Claude's PascalCase events and payload (`tool_name` carries Claude names such as `Bash`), runs `command` under bash or PowerShell, sets `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA`, and honours `hookSpecificOutput.permissionDecision` `allow|deny|ask`. One file serves every harness, with no `--experimental`.
- **VS Code reads the same file.** VS Code (1.139) detects the plugin as Claude format from `.claude-plugin/plugin.json`, loads `hooks/hooks.json`, maps both PascalCase and Copilot camelCase event names, sets `CLAUDE_PLUGIN_ROOT` but not `CLAUDE_PLUGIN_DATA` (state falls back to `<tmpdir>/guard-plugin-<uid>`, created `0700`), and **ignores `matcher`**: every command of an event runs, so each script checks `tool_name` itself and passes anything else untouched. VS Code sends its own tool names (`run_in_terminal`, `create_file`, ...) and reads `permissionDecision` and `additionalContext` from `hookSpecificOutput`.
- **One output, every reader.** Where the harnesses read different fields, the hook writes both: post-edit lint puts `additionalContext` at the top level (Copilot CLI) and in `hookSpecificOutput` (Claude, VS Code); the stop hook puts `decision`/`reason` at the top level (Claude, Copilot CLI) and in `hookSpecificOutput` (VS Code). Claude and Copilot CLI accept the extra fields (checked live).
- **State in a file.** A command hook is a fresh process, so the loaded skills and the rules already reminded live in `$CLAUDE_PLUGIN_DATA/sessions/<session_id>.jsonl` as append-only facts, one JSON line each (`{"loaded":"ship"}`, `{"reminded":"edit","agent":"a1"}`). Each hook appends only its new facts in one `O_APPEND` write, which the OS keeps whole, so parallel hooks lose nothing and need no lock. Skill loads count for the whole session, subagents included; reminders count per agent (`agent_id`, which Claude Code sends from a subagent; the other harnesses send none, so their subagents share the main agent's reminders, [#172](https://github.com/giocaizzi/harness/issues/172)). An event without a session id keeps nothing.
- **Remind once, ask every time.** A skill rule denies once per session with the skill to load; the title guard denies every time the subject of `git commit -m` (the first `-m` only; a `"$(cat <<'EOF' …)"` heredoc and `-F -`/`--file=-` with a heredoc are read), `gh pr create|edit --title`/`-t`, `glab mr create|update --title`/`-t` or `az repos pr create|update --title` does not match the org's PR-title check exactly (`^type(\(scope\))?!?: [a-z].*$`, scope `[a-z0-9._/-]`; az's `-t` is the target branch, so only `--title` counts). Every titled command in a chain or payload is checked, only at command position (`echo git commit -m x` sets none); a variable or a message file is unreadable and passes, and git's `Merge …` subjects are skipped; risky commands return `ask` every time, with a read-only blast-radius preview (`du -sh` of the delete's own targets, resolved through `cd`, `~` and variables; `git status --short`; `git log HEAD..@{u}`).
- **Hints for skills the agent misses.** A skill rule with `remind: true` (`pr-fix` on `gh pr view --comments`, PR comment API calls or `gh run view --log-failed`; `pytest` toward `python-testing`) and a `files` rule (an edit under `docs/` or to `README.md`/`AGENTS.md` toward `docs-sync`) add a once-per-session hint as `additionalContext` instead of denying. A whole command that only prints files (`cat f`, `head -n 5 f`, `sed -n 1,40p f`) gets a once-per-session hint toward the harness's read tool, except on Codex, which has none. A shell file edit gets a once-per-session hint toward the edit tool, because the post-edit lint and the `files` hints run only on edit tools: `sed -i` (`-I`, `--in-place`), `perl -pi`/`-i`, inline Python (`-c`, a heredoc) with `open(…, 'w'|'a'|'x')` or `Path(…).write_text`/`write_bytes`/`open('w')`, inline Node (`-e`, `-p`, a heredoc, `deno eval`) with `writeFileSync`/`appendFile*`/`createWriteStream`, and `echo`, `printf`, `cat` (with a heredoc too), `tee`, `Set-Content`, `Add-Content`, `Out-File` into a file. A write to `/dev/*`, `$null`, an fd (`>&2`), stderr (`2>`) or a temp path (also through a literal path in the Python or Node call) is not an edit; other commands' output redirected to a file (`jq … > f`, `make test > log`) is left out, as tool output rather than hand-written content. Codex hooks can only add a `systemMessage`, so no hint reaches its model ([compatibility.md](compatibility.md)). Each hint is logged as `guard.reminder`, so a miss is counted. Edits reach the hook because the `PreToolUse` matcher includes the edit tools.
- **Every spelling of a risky command, payloads included.** Rules match what runs, not text a command carries: quoted strings and heredoc bodies are blanked, so `rg -c 'rm -rf x' f`, `echo 'rm -rf /'` or a commit message naming a command pass. What runs although it is written as data is read again (`core/shell.mjs`) and judged by the same rules: the string after a shell's `-c` in any flag spelling (`bash -lc`, `sh -c --`, `$'…'` quoting, behind `sudo`, `env`, `xargs`), `eval`, `cmd /c`, `powershell`/`pwsh -Command`, a heredoc or `echo`/`printf`/`cat <<EOF` piped into a shell, `$(…)` and backticks even inside double quotes, `docker`/`podman`/`kubectl exec`, and `ssh`'s remote command, three levels deep. Remote and container payloads get the local rules unchanged (owner decision D4): a remote `rm -rf /tmp/x` is a temp delete; but no fact about this machine (worktree, branch, git-ignored output) is gathered for another host's paths, so any other remote delete asks, naming the host. Heavy commands on another host do not trip the local host guard. What cannot be read asks as `opaque`: `-EncodedCommand`, `base64 -d`/`xxd -r`/`openssl -d` piped into a shell, payloads nested more than three levels. A pipe into a shell from anything else (`curl … | sh`) is not read and not asked about. Rules match with git's global options removed (`-C dir`, `-c k=v`, `--git-dir`, `--work-tree`, `--no-pager`, any combination), so `git -C x reset --hard` asks and `git -C x commit -m "bad"` is denied like the plain form; a relative target after `git -C dir` is judged as `dir/target`. A `.git` URL is not a git command (`git push https://h/r.git --force main` still asks). Recursive delete covers `\rm`, `command rm`, `/bin/rm`, `sudo rm`, `xargs rm`, `Remove-Item -r`/`-Rec`/`-Recurse:$true`, `ri`, `rd /s`, `rmdir /s`, `del /s`; `find` with `-delete` or `-exec`/`-execdir rm` asks too (find walks a whole tree, so any delete it runs is recursive). Git forms that lose work git cannot restore: `git clean -f` (not with `-n`/`--dry-run`), `git checkout`/`git restore` of the whole tree, a directory (`dir/`) or a glob (`.`, `:/`, `*.ts`; `restore --staged` alone only unstages) and `checkout -f`, `switch -f`/`--discard-changes`, `git stash drop`/`clear` (only `git fsck` finds the stash again), `git branch -D` (or `-d -f`; case-sensitive, since `-d` refuses an unmerged branch), `git rm -f` without `--cached`, `git push --mirror`/`--prune`, and `git push --delete`/`-d`/`:` of `main` or `master`. Left out, as recoverable or narrow: `git checkout -- f` and `git restore f` of one named file (a deliberate revert; asking each time teaches blind approval), `git rm` without `-f` and `git rm --cached` (the files are in git; `git rm -r` no longer asks as a recursive delete), `git push --delete` of another branch, `git stash pop` (keeps the stash on conflict), `git branch -d`, and aliases (`git co .`), which the hook cannot resolve. Codex and opencode prompt rules match from the first word, so a form with git's global options or a `find` delete is never a plain prefix there: they are denied with "ask the user to run it", as is `git push --delete main` (a prefix would also ask for every feature branch); `git clean -f…`, `git checkout .`, `git restore .`, `git stash drop`, `git branch -D`, `git rm -f`, `git push --mirror`/`--prune` have prefixes. Installing a new guard version needs `make install HARNESS=codex` again (the rules file changes; until then every risky command is denied on Codex, by design).
- **Data loss outside git (owner decision D3).** Asks: `docker`/`podman volume rm`/`prune`, `system prune`, container removal with its volumes (`docker rm -v`, `docker compose down -v`) (`docker`); `gh repo|release|secret delete` and `gh api -X DELETE` (`gh-delete`); `kubectl … delete`, `helm uninstall`/`delete` (`k8s`); `gcloud … delete`, `az … delete` (`cloud-delete`); `dd … of=/dev/…`, `mkfs`, `diskutil erase…` (`disk`); `terraform`/`tofu apply`/`destroy`, global options such as `-chdir=` included (`terraform`). Git forms git cannot restore from the remote ask as `rewrite`: `git update-ref -d`, `git filter-repo`/`filter-branch`, `git branch -f main`. Left out on purpose: routine `docker rm`/`rmi` of disposable containers and images, `docker image prune`, `docker stack rm`, `chmod -R`, `rsync --delete`, a plain `git push origin feat:main` (the branch ruleset rejects it). `git reset --hard` asks wherever `--hard` sits (`git reset HEAD --hard`); a lease push naming main or master anywhere asks; `--force-if-includes` alone does not. Codex and opencode prompt for the plain forms (`docker volume rm`, `gh repo delete`, `kubectl delete`, `helm uninstall`, `tofu destroy`, `mkfs`, …); `gcloud`/`az` deletes have no first-word prefix and are denied there.
- **Safe deletes.** A delete with no target the hook can read (`xargs rm -rf`, `find -delete` without a start path) always asks, also next to a safe target. `rm -r`, `Remove-Item -Recurse`, `find -delete` (its start paths) and `git worktree remove --force` skip the ask when every target is strictly under a temp dir (`/tmp`, `/private/tmp` but not the tmux, X11 or ssh sockets there, the macOS per-user `/var/folders/<a>/<b>/T/`, a Windows user's `AppData\Local\Temp`, or the environment's own `TMPDIR`/`TEMP`/`TMP`), is git-ignored regenerable output, or is the root of a linked worktree that is clean, holds no git-ignored secret (`.env*`, `*secret*`, `*.key`: they exist nowhere else), and either has every commit on a remote ref or is squash-merged: `gh pr list --head <branch> --state merged` (run in the worktree, 5 s timeout) finds a merged PR whose head contains HEAD. Any gh failure asks, with the reason. Worktrees are checked in parallel. A `for VAR in w1 w2; do …; done` whose list holds only plain words is expanded once per word, so `for w in a b; do git worktree remove --force .claude/worktrees/$w; done` is judged per target; a list with globs, quotes or `$(…)`, a body that assigns or reads VAR, or a nested loop is not expanded and asks. A relative target after `cd DIR` (plain DIR, `;`/`&&` chains only) is checked as `DIR/target`; any other `cd`, or a subshell, group, `||`, `pushd` or conditional next to a `cd`, makes relative targets ask. Paths resolve the way the shell would, by position (owner decision D5): a leading `~` or `$HOME` from the hook's environment (`USERPROFILE` on Windows), in `cd`, `git -C` and the targets alike, and `$NAME` from an assignment earlier in the same command (`NAME=/abs/path`, `NAME=$(mktemp -d)`, `export NAME=…`; the latest wins, and a non-path value forgets it). A prefix assignment (`NAME=/tmp/x cmd && rm -rf $NAME`) holds for that one command, so it is not followed, and neither is an assignment after the delete, inside `echo`, or a variable from the environment: those ask, as do `~user`, globs outside a temp dir, `..` and quotes. So `cd ~/repo && git branch -D feat` gets its branch facts in `~/repo`, and `SP=/private/tmp/x; cd $SP && rm -rf out` is a temp delete. The pip deny is judged in the repo the command runs in (`cd <uv repo> && pip install x`), and the edit hint ignores writes to a temp dir reached through `cd` or a variable, and `sed -i`/`perl -pi` of temp files. Regenerable output: the last path segment is one of `node_modules`, `.venv`, `venv`, `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.terraform`, `dist`, `build`, `.next`, `target`, `coverage`, `.turbo`, `.cache`, `.wrangler`, `.vitest-cache`, `.vite`, `.gradle`, `.parcel-cache`, `.svelte-kit`, `.nuxt`, or `results` under `evals/` (not `out`: a source folder in some stacks); no segment looks like a secret (`.env*`, `*secret*`, `*.key`); and `git -C <parent> check-ignore -q -- <name>` succeeds, which also proves it is inside a repo and untracked (tracked files under it are in git anyway). A glob, an unresolved `cd` or a check that fails asks. `git branch -D` skips the ask when every branch it names has no commit off the remote refs (`git rev-list --count <b> --not --remotes` is 0) or its tip is in the head of a merged PR of that name (squash merge, remote branch deleted; the same `gh` check as worktrees); otherwise the ask says why per branch.
- **Readable asks.** An ask (and a deny the agent reads) starts with what the risky part does in plain words, with the targets the guard resolved: `Risky command: Deletes 2 paths recursively: sub/build, sub/dist.` (after `cd sub`), `Force-pushes origin feat.`, `Deletes branches a, b.`, `… on pi.local.` for an ssh payload; then `Step:` the risky pipeline on its own when the command has more than that; then `Rule:` the rule id and why; then the facts that made it ask (`Worktree x: 2 unpushed commits`). A risky step buried in a long command is denied instead, with "Run the risky step as its own simple command … Then retry": when the whole command chains more than 3 commands, or when the step sits in a `bash -c`, `eval` or `ssh` payload next to 2 or more other commands (owner decision D15). A shorter chain just asks. Logged as `guard.decision` with `via=split`.
- **Secret reads ask, injection passes.** Two risky rules ask every time, with a reason naming the `secrets-handling` skill: `secrets` (`bw`/`bws` `get`, `list`, `run`, `unlock`, `login`, `export`, `serve`, `bws secret`; `security find-generic-password`/`find-internet-password` with `-w` or `-g`; `chezmoi secret keyring get`; `op read`, `op item get --reveal`; `pass show`; `gcloud secrets versions access`; `az keyvault secret show`; `printenv` of a TOKEN, SECRET, KEY, PASS or CREDENTIAL name; the CLIs' own token printers, `gh auth token`, `gh auth status --show-token`, `gcloud auth print-access-token`/`print-identity-token`, `az account get-access-token`; `security dump-keychain`; a bare `env` or `printenv` dump, alone or piped to anything but a filter (owner decision D9); any reader (`cat`, `less`, `head`, `tail`, `bat`, `grep`, `rg`, `sed`, `awk`, `cut`, `jq`, `source`, `.`, a `<` redirect) of a `.env`, `.env.<name>` or `.envrc` file (`.env.example`/`.sample`/`.template`/`.dist` excepted, also when quoted: `cat ".env"`), `~/.netrc`, `~/.aws/credentials` or a private `~/.ssh/id_*` key (not `.pub`); and `echo`, `printf` or `Write-Output` of a variable named `*_TOKEN`, `*_KEY`, `*_SECRET` or `*PASSWORD`, quoted or not (`$KEY_PATH` passes)) and `secrets-env` (`printenv` or `env` piped to `grep`, `rg`, `findstr` or `Select-String` when that pipeline names TOKEN, SECRET, KEY, PASS, CREDENTIAL, TOK, GH_, PAT or BEARER; its `raw` pattern reads the pipeline as written, since the grep pattern is usually quoted, and only that pipeline, so a secret word elsewhere in the command does not count; a pipeline that ends keeping only the names, `cut -d= -f1`, `sed 's/=.*//'` or `awk -F= '{print $1}'`, prints no value and passes). `printenv <name>` of another variable and `env | grep PATH` pass. An ask, not a deny: reading a secret is often the task, and the user decides. A token injected for one command, `VAR="$(<keyring read>)" ./script` (also `export VAR="$(…)"`, also inside `bash -c`), passes without asking: the secret rules (`skipInjected`) do not look inside a double-quoted `$(…)` that is the whole value of an assignment, since the value goes to an environment, never to output, which is what `secrets-handling` prescribes; asking there would teach the user to approve blindly. Every other rule still reads it (`x="$(rm -rf src)"` asks). Unquoted, `VAR=$(...)` asks, and so does `echo "$(bws secret get x)"`. `bws run -- <cmd>` asks: it hands every project secret to a command the hook cannot vet. Codex and opencode prompt for the plain forms in the rule's `prefixes` (also `gh auth token`, `gcloud auth print-access-token`, `az account get-access-token`, `security dump-keychain`); `security find-…-password`, `op item get --reveal`, `printenv`, a bare `env`, the `env` pipes and echoed secret variables are denied there with "ask the user to run it". These replace the old `secrets` skill reminder.
- **Fail open for reminders, closed for risky.** A crash while judging a risky command denies it; anything else lets the call through. The script never exits non-zero, because Copilot denies a `preToolUse` whose hook fails. A hook timeout is fail-open on both harnesses.
- **Deny rules are data, scoped to the repo.** `rules.deny` (pip, pipx, `python -m pip`; poetry) is matched on what the command would run, so a quoted mention passes. pip is denied only at command position (owner decision D13): `pip install|uninstall|download|wheel` (also `sudo pip3`, `.venv/bin/pip`, `python3 -mpip`), `pipx install|run|inject|upgrade|reinstall`; `which pip`, `git log --grep pip`, `echo pip install`, `uv pip …` and read-only `pip list`/`pip freeze` pass. A rule with `when: "uv"` denies every time, before anything else, only in a uv repo; elsewhere the command runs and the agent gets one note per session (`hookSpecificOutput.additionalContext`, no permission decision) naming the repo's manager. Copilot CLI (1.0.95) passes that note to the agent too (checked live), and VS Code documents `additionalContext` on `PreToolUse`. The hook finds the manager in the nearest directory up to the repo root: `uv.lock` → uv; `poetry.lock` or `[tool.poetry]` → poetry; `Pipfile`/`Pipfile.lock` → pipenv; `requirements*.txt` without a `pyproject.toml` `[project]` table → pip; any other `pyproject.toml` → uv; none → no Python project. Plain `node:fs` calls, the same on every OS; a read error counts as no project.
- **Stop runs `make check-fast` or `make check` once, and only on change.** A repo whose full check is slow defines `check-fast` (lint, types, quick tests) and the hook runs that; otherwise it runs `check`, and CI keeps the full suite either way. No make, no Makefile or neither target: the agent stops. The hook fingerprints the repo (`HEAD`, `git diff HEAD`, untracked file names) and skips the check when it equals the last green run, stored under `$CLAUDE_PLUGIN_DATA/stop/`; outside git it always runs. A failure blocks the stop with the last 40 lines; the next stop (`stop_hook_active`) always passes, so it cannot loop (Copilot also caps at 8 blocks). The check times out after 1750 s (`GUARD_STOP_TIMEOUT_MS` overrides; the hook limit is 1800 s). A timeout is shown as a `systemMessage`, never blocks and never counts as green. The check never becomes the bottleneck: on a strained host (the guard's `host` caps: load or free disk) or while another stop check runs in the same repo (a pid lock under `stop/`), it is deferred with a `systemMessage` and nothing is marked green, so the next stop runs it. `GUARD_STOP_CHECK=off` disables the hook.
- **Lint is advice, not a block.** Findings come back as `hookSpecificOutput.additionalContext`; a missing shellcheck, pwsh or PSScriptAnalyzer skips silently. The file path is `tool_input.file_path` (Claude) or `tool_input.path` (Copilot).
- **Keep-awake follows the harness.** The hook walks past shell parents to the harness pid (under VS Code, the extension host: the keeper lives as long as the window) and starts a detached keeper bound to it: `caffeinate -i -w <pid>` (macOS), `systemd-inhibit --what=idle:sleep tail --pid=<pid> -f /dev/null` (Linux), a hidden PowerShell holding `SetThreadExecutionState(ES_CONTINUOUS|ES_SYSTEM_REQUIRED)` until `Wait-Process -Id <pid>` (Windows). The keeper pid is kept in `$CLAUDE_PLUGIN_DATA/awake/<harness pid>.pid`, so resume, `/clear` and compaction reuse it. It prevents idle sleep only; the display may still sleep.
- **Codex: generated hooks file, prompt rules for the ask.** Codex rejects a hooks file with the Claude-only `modules` key and does not support `ask` (it marks the hook failed and runs the command). `build_agents.py` writes `.generated/codex/hooks.json` without `modules`, with `--no-ask` on the guard command. With `--no-ask` a risky command of single-spaced plain words (no `$`, `~`, globs, quotes, escapes or operators, which Codex does not parse and so runs without its prompt rules) starting with a rule's `prefixes` passes the hook, and Codex's own prompt rule asks. It does so only when `$CODEX_HOME/rules/giocaizzi-guard.rules` equals this version's `codexRules`, so a stale or missing file never lets a command through unasked, and only when the session's last `turn_context` in the rollout (`transcript_path`) has `approvals_reviewer` `"user"`: that is the effective value from config, profiles, `-c` and `--approve-for-me`, and an AI reviewer could approve the prompt. No record denies. Any other risky command is denied with the reason and "ask the user to run it" ([#69](https://github.com/giocaizzi/harness/issues/69); why not `PermissionRequest`: [compatibility.md](compatibility.md#decisions)). Codex sets `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA`, so the scripts run unchanged. Plugin hooks run only once trusted in `/hooks`.
- **opencode and pi in-process.** Neither runs command hooks, so `bridge.mjs` calls the handlers directly. They set no data dir: state falls back to `<tmpdir>/guard-plugin-<uid>`, as on VS Code. opencode cannot ask from a plugin, so its `config` hook appends `permission.bash` ask entries for the same prefixes (last, after `*`, so they beat a user's `allow`) and the guard leaves a covered plain command to opencode's prompt; other forms, a user `deny` on `bash` or `*` (the entries are then skipped), `opencode run --auto` in any spelling (`--auto=true`; it approves every ask) and a session with its own bash rule are denied like Codex.
- **Known limits of the borrowed prompts.** The hook cannot see `opencode run --attach <url> --auto` (the client approves; the server's argv lacks the flag): there `--auto` approves a covered plain command. Persistent approvals (Codex "don't ask again", opencode "Allow always") can cover a whole prefix for later commands. Codex on Windows wraps commands in PowerShell; its prompt rules there are untested. Details: [compatibility.md](compatibility.md#decisions). pi asks through `ctx.ui.confirm` and blocks when there is no UI (`-p`, JSON mode). Neither can block a stop: the failure is sent back as a new message once, and the next idle or settle passes. `make check` runs synchronously, so the harness waits for it.
- **Skills read, not invoked.** Codex and pi have no skill tool: a shell or read call that touches `skills/<name>/SKILL.md`, a prompt starting `$name` (Codex) or `/skill:name` (pi) counts as loading it.
- **The mod is Claude-only.** Copilot CLI and VS Code have no mods API and no rate-limit windows, so the throttle has no Copilot side.
- **`ask` is the harness's own prompt.** Under `claude -p` or a non-interactive Copilot run nobody can answer, so the risky command does not run.
- **The skill enforcer counts the `skill` tool.** Claude's `Skill`, Copilot CLI's and VS Code's `skill` record the loaded skill; a skill read any other way is not seen, so the reminder fires once and the retry passes.

## Unattended and auto-approve runs

Hooks run before the harness applies its permission mode, so a deny holds under accept-edits, bypass, `--allow-all`, `--auto` and `-a never` alike. Only the risky-command `ask` depends on the mode.

- **`GUARD_UNATTENDED=1`** (also `true`, `on`) makes `handle` turn every risky `ask` into a deny: "Unattended run: nobody can confirm this, so the command was not run. Pick another approach, or leave it for the user." It sits before the `noAsk` branch, so it covers every harness the same way (Codex through `--no-ask`, opencode and pi through `bridge.mjs`), including a plain command a native prompt would have covered. Safe deletes (temp dirs, clean pushed or merged worktrees) still pass, since they never ask. Export it in the shell that launches the harness; hooks inherit the environment.
- **Without it**, an interactive session waits at the first risky command until someone answers, and a headless run (`claude -p`, `copilot -p`, `codex exec`, `opencode run`, `pi -p`) cannot ask, so the command does not run. Codex under approval `never` rejects a prompt rule; `opencode run --auto` approves every ask, so the guard denies there.
- **Not verified live:** whether Claude Code's bypass mode, Copilot CLI's `--allow-all` and VS Code's auto-approve still show a hook `ask`. Treat the risky ask as unreliable there and set `GUARD_UNATTENDED=1`, which does not depend on it. (A live probe of Claude bypass was refused by the session's own auto-mode classifier, so it was not run.)
- **Other gates that can pause an overnight run:** the host guard (load over 30, CPU over 90 %, under 20 GB free) delays heavy builds and tests; the Claude-only usage throttle pauses near 90 % of the plan window; the stop hook runs `make check` once. Codex hooks do nothing until trusted in `/hooks`.
- **Ask timeout (Claude Code).** The mod's `tool.check` hook puts every permission ask that would reach the person (the guard's risky ask, an `ask` rule, a tool not yet allowed) in its own Allow/Deny dialog and parks it after 60 seconds without an answer, in every mode, attended included: the user may be busy in another session, and a session must not wait on a dialog. Parked means denied with "No answer … This is not a refusal. Carry on with the rest of the task without it, or park it: say in your report that it is waiting for the user's approval", never "the user denied this call". A dialog that cannot show or is dismissed (headless, a host without one) gets the same no-answer wording. Only an explicit Deny says "The user denied this call. Do not retry it or a respelling of it; ask the user what they want instead." Under `dontAsk` the mod leaves the ask to the engine, which denies anything not pre-approved. Each outcome is logged as `guard.ask_result` (`result` allow, deny, timeout or unavailable, `wait_ms`, `tool`, `tool_use_id`). `GUARD_ASK_TIMEOUT_MS` (whole milliseconds, in the environment that launches Claude Code or the `env` block of its settings) changes the wait; `0` turns the timeout off and leaves the ask to the engine's dialog; any other value keeps 60 seconds. Left to the engine: auto mode's own asks (its classifier answers them; a hook's ask in auto mode is still taken), a hosted session's asks, `AskUserQuestion` and `ExitPlanMode`. The dialog has no "always allow" and no diff preview. A failing hook falls back to the engine's dialog. The mode comes from the last prompt or tool result, so one ask right after a shift+tab mode switch can go the old way. Claude's own questions time out natively: `askUserQuestionTimeout: "60s"` in user settings (the dotfiles set it) continues them with the answers picked so far. Other harnesses: pi and opencode can do it ([#100](https://github.com/giocaizzi/harness/issues/100)); Codex, Copilot CLI and VS Code cannot ([#101](https://github.com/giocaizzi/harness/issues/101)).
- **Agent-side rules** (worktree per task, no reliance on denied commands, report what was blocked): the `dev-tools` skill `unattended-runs`.

```bash
# then set chat.plugins.enabled and "chat.pluginLocations": { "<abs>/plugins/guard": true },
# and check the plugin and its hooks under Chat: Open Agent Customizations

# The hook by hand: a non-conventional commit is denied
echo '{"hook_event_name":"PreToolUse","session_id":"t","tool_name":"Bash","tool_input":{"command":"git commit -m bad"}}' \
  | CLAUDE_PLUGIN_DATA="$(mktemp -d)" node plugins/guard/hooks/guard.mjs
```

In a uv repo: `pip install x` and `poetry add x` are denied; in a poetry or requirements repo they run, with one note. In any session: ending a turn in a repo whose `make check` fails continues the turn once with the failure; `pmset -g assertions | grep caffeinate` (macOS) or `systemd-inhibit --list` (Linux) shows the keeper; `git commit -m "bad"` is denied with the Conventional Commit hint; `rm -rf build` shows the permission prompt with a `Would affect:` preview (Codex and opencode: their own prompt, no preview); `rm -rf /tmp/x` runs without asking (Codex and opencode ask anyway: their prompt rules match the prefix).

## Grafana

Each deny or ask (`guard.decision`, from the command hook, with `tool_use_id` to join the harness's own tool decision), each stop check (`guard.stop`: `result` pass, fail, timeout or deferred, `target`, `duration_ms`; on a failure also `failed_target`, the innermost make target, and `last_line`, the output's last line with secrets masked and cut to 200 characters), each skill hint (`guard.reminder`: `rule`), each skill loaded in a session (`guard.skill`: `skill`, `via` tool or prompt; a typed `/name` counts only for this marketplace's skills, so built-in commands stay out), each answer to an ask the guard sees (`guard.ask_result`: `result` allow, deny, timeout or unavailable, `wait_ms`; from the Claude mod's dialog and from pi's confirm, where no UI is `unavailable` with `via=no-ui`; Copilot CLI and VS Code answer asks inside the harness, which reports them in its own `tool_decision`, [#158](https://github.com/giocaizzi/harness/issues/158); Codex and opencode never ask through the guard) and each usage-throttle denial (`guard.throttle`, from the Claude mod) is sent as one OTLP/HTTP log record to `$OTEL_EXPORTER_OTLP_ENDPOINT/v1/logs`. Claude Code and Copilot CLI strip `OTEL_*` from command hooks, so the hook falls back to `GUARD_OTEL_EXPORTER_OTLP_ENDPOINT`, `GUARD_OTEL_EXPORTER_OTLP_HEADERS` and `GUARD_OTEL_RESOURCE_ATTRIBUTES` from the shell that launched the harness (the dotfiles export them on personal machines with an endpoint). The Claude mod reads the same pairs (`OTEL_*`, else `GUARD_OTEL_*`). Nothing is sent when neither is set: the work machines and a VS Code started outside such a shell stay silent. The auth headers come from `OTEL_EXPORTER_OTLP_HEADERS` and are never logged; a send that fails or takes longer than 2 s is dropped and the decision stands.

`guard.decision` logs the effective action, after the harness transforms: an ask turned into a deny is `action=deny` with `via=unattended` (`GUARD_UNATTENDED`) or `via=no-ask` (Codex, opencode: no prompt covers the form), and an ask left to the harness's own prompt is `action=ask` with `via=native-ask`. It carries `cmd_hash` (12 hex characters of the sha256 of the command, whitespace collapsed) to count repeats, never the command text. A host deny (`rule=host`) carries `load1`, `cpu_percent` and `free_gb`.

Every record carries `harness` (`claude`, `copilot`, `vscode`, `codex` from the `--harness=codex` flag the Codex hooks file passes, `opencode`, `pi`), `guard_version` (the installed plugin's) and `repo` (the name of the git top level of the hook's cwd, read only when a record is sent).

The resource carries `service.name=guard` plus `OTEL_RESOURCE_ATTRIBUTES` (`service.namespace`, `host.name`). In Loki: stream labels `service_name`, `host_name`, `service_namespace`; structured metadata `rule`, `action`, `via`, `result`, `tool`, `harness`, `guard_version`, `repo`, `window`, `percent`.

**Factory events file.** When `FACTORY_EVENTS_FILE` is set (a factory runtime sets it for the runs it starts, [factory.md](factory.md)), each `guard.decision` is also appended to that file as one JSON line `{"ts", "decision", "rule", "cmd_hash"}`: `ts` ISO 8601, `decision` the effective action (`deny` or `ask`, as above), never the command text. It works in every harness, with or without an OTLP endpoint and whatever `GUARD_OTEL` says; a write that fails is dropped and the decision stands. The runtime's guard deny-rate breaker reads it.

Verify: after a denied command, `{service_name="guard"}` in Grafana Explore shows the record; `sum by (rule) (count_over_time({service_name="guard"} | rule != "" [1h]))` counts denials per rule.

`GUARD_OTEL=off` (also `0`, `false`) sends nothing, whatever the endpoint. `make test` sets it, and so must any probe that spawns `hooks/guard.mjs` or imports the engine from a shell that exports the collector: fake sessions otherwise land in the real telemetry.

### Usage for opencode and pi

Neither exports telemetry, so the in-process guard reports for them, with the same endpoint and headers: one `api_request` log record per finished assistant message, as service `opencode` or `pi` (it owns `service.name` and `service.namespace`), with `session.id`, `model`, `provider`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `reasoning_tokens` and `cost_usd`. opencode prices the message itself (`cost`); pi prices it at its catalog rate (`usage.cost.total`). The names follow Claude Code's `api_request`, so one query covers every harness. Claude Code, Copilot CLI, VS Code and Codex export their own (enabled by the dotfiles); see the compatibility matrix.

## Regression corpus

`core/corpus.json` holds real commands from the guard reviews (telemetry, transcripts, code audit), paraphrased with hosts and paths anonymised and no secrets, each with the decision the guard must reach: `allow`, `allow:<hint>`, `ask:<rule>` or `deny:<rule>`, the bug id and the source. `core/corpus.test.mjs` runs each row through `evaluateCommand` with a fixed environment (`HOME=/Users/me`, a macOS `TMPDIR`) and favourable facts (every branch pushed, every regenerable name git-ignored, no linked worktree), so a row asks only where the guard cannot reach or read the facts. A row whose bug is still open runs as `todo`, so the suite stays green; the PR that fixes the bug removes its id from `OPEN` and the rows become enforced. Control rows (`control`, `probe`) are always enforced.

Every guard false ask or missed command found in telemetry (`/agent-review`) or a transcript becomes a row, with a bug id, before or with its fix.

## Troubleshooting

| Symptom | Check |
|---|---|
| No guard at all | Plugin enabled? Claude: `/plugin`; Copilot: `copilot plugin list`; VS Code: `chat.plugins.enabled`, `chat.useHooks` and the Agent Customizations editor; Codex: `codex plugin list`, then trust the hooks in `/hooks`; opencode: `~/.config/opencode/plugins/giocaizzi-guard.js` exists and points at a checkout that is still there; pi: `pi list`. `node` on PATH (22+)? |
| Codex warns `failed to parse plugin hooks config` | An old guard without a Codex-only hooks file: `codex plugin marketplace upgrade`, then re-add the plugin. |
| Every shell call denied on Copilot | The hook exits non-zero (Copilot fails `preToolUse` closed): run it by hand as above and read stderr. |
| Session never ends a turn on Copilot | `make check` keeps failing: the agent gets 8 blocks at most, then stops. |
| Machine still sleeps | Keeper running? `pgrep -fl caffeinate` / `systemd-inhibit --list`; on Linux `systemd-inhibit` needs a logind session. |
| A reminder repeats | In a subagent: reminders count per agent, so each subagent gets a hint once (Claude Code). Otherwise the data dir is not writable: check `sessions/<session_id>.jsonl`. |
