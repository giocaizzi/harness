# guard plugin

Agent rules enforced as hooks, from one plugin, for Claude Code, Copilot CLI, VS Code Copilot (agent plugins), Codex CLI, opencode and pi on macOS, Linux and Windows. What differs per harness: [compatibility.md](compatibility.md).

## Architecture

| Piece | Role |
|---|---|
| `core/rules.mjs` | Data: skill rules (command pattern -> skill), deny rules, heavy and risky command patterns (each risky rule with the `prefixes` Codex and opencode prompt for), title types, host caps, usage thresholds. |
| `core/shell.mjs` | A small shell reader: splits a command into simple commands, blanks quoted text, drops heredoc bodies and comments, and finds payloads that run as code (a shell's `-c`, `eval`, `ssh`'s remote command, `docker`/`kubectl exec`, `cmd /c`, `powershell -Command`, a heredoc or `echo`/`printf` piped into a shell, `$(…)` and backticks, `<(…)`, `>(…)` and zsh `=(…)`), read again three levels deep. A `(` right after `=`, `@`, `?`, `*`, `+` or `!` (a bash array `x=(a b)`, an extglob `@(a|b)`) stays part of its word, and so does any whitespace but a blank or newline (a vertical tab, form feed or Unicode space), as in the shell. |
| `core/engine.mjs` | Pure decisions: `evaluateCommand` (risky ask, title guard, host guard, skill reminder, read and edit hints), `evaluateRouting` (the routing hint on subagent spawns), `evaluateSpawn`, blast-radius preview argv, safe-delete facts (worktrees, branches, ignored build output) through an injected runner. |
| `core/host.mjs` | Host-fact parsers (load average, free disk, Windows CPU percent). |
| `core/docsonly.mjs` | Pure: whether a change set is docs only, by the default skip list and the repo's `.stop-check-ignore`, so the stop check can skip it. |
| `hooks/hooks.json` | Command hooks, Claude format. Claude Code, Copilot CLI and VS Code load it from the installed plugin. |
| `.generated/codex/hooks.json` | Generated by `make build` for Codex: `hooks.json` without `modules`, the guard run with `--no-ask`. `.codex-plugin/plugin.json` points Codex at it. Its prompt rules (`$CODEX_HOME/rules/giocaizzi-guard.rules`) come from `scripts/install.mjs`, rendered by `codexRules` from the risky rules' `prefixes`. |
| `hooks/bridge.mjs` | The guard for in-process harnesses: turns an event into the Claude-shaped payload and calls the same `handle`, `lintFile`, `stopCheck` and `keepAwake`. |
| `hooks/opencode.mjs` | opencode plugin over the bridge; `scripts/install.mjs` writes a stub in `~/.config/opencode/plugins/` that re-exports it. |
| `hooks/pi.mjs` | pi extension over the bridge, listed in the repo's root `package.json`. |
| `hooks/guard.mjs` | The command guard: reads the event on stdin, gathers facts (host, worktrees, the repo's Python manager), asks the engine, writes `hookSpecificOutput` on stdout. |
| `hooks/stop.mjs` | The factory result gate, then `make check-fast` (when defined) or `make check` before the agent stops (was the dotfiles `stop-make-check.sh`/`.ps1`). |
| `.generated/factory/check-result.mjs` | Generated by `make build`: a copy of the `factory` plugin's result checker, which the result gate imports (the plugins install separately, so a hook cannot import across them; `make validate` fails when the copy drifts). |
| `hooks/lint.mjs` | shellcheck / PSScriptAnalyzer after an edit (was the dotfiles `post-edit-lint.sh`/`.ps1`). |
| `hooks/awake.mjs` | Keep-awake keeper tied to the harness process. |
| `hooks/mod.mjs` | Claude Code mod (`modules` in `hooks.json`, ignored by Copilot CLI and VS Code): the usage throttle and the ask timeout. The UI (band, pane, status line, spinner) is the `hud` plugin ([docs/hud.md](hud.md)); toasts and sounds are the `sounds` plugin ([docs/sounds.md](sounds.md)). |

Events:

| Event (Claude and VS Code / Copilot CLI) | Tools (matcher, re-checked in the script) | What runs |
|---|---|---|
| `SessionStart` / `sessionStart` | all | Keep-awake keeper, one per harness process. One `guard.session` record per session and harness process (plugin versions). |
| `PreToolUse` / `preToolUse` | Shell: `Bash`, `PowerShell` (Claude), `bash`, `powershell` (Copilot), `run_in_terminal` (VS Code). Skill: `Skill`, `skill`. Spawn: `Agent`, `Task` (Claude), `task` (Copilot) | Shell: deny rules (pip, poetry), risky ask, title guard, host guard, skill reminder. Skill: records the loaded skill. Spawn: the routing hint. |
| `PostToolUse` / `postToolUse` | `Edit`, `Write`, `MultiEdit` (Claude); `edit`, `create`, `Edit` with an apply_patch string (Copilot); `create_file`, `replace_string_in_file`, `multi_replace_string_in_file`, `insert_edit_into_file`, `apply_patch` (VS Code) | Lint the edited files; findings as `additionalContext`. |
| `Stop` / `agentStop` | all | In a factory run, the result gate: `decision: block` at most twice per run while its `result.json` is missing or invalid. Then `make check-fast` (when defined) or `make check` when the repo changed since the last green run and the change is not docs only; a clean first turn skips it unless `GUARD_STOP_CHECK=force` requests it. On failure, `decision: block` once, never when `stop_hook_active`. Both block as one. |
| `UserPromptSubmit` / `userPromptSubmitted` | all | A typed `/skill` counts as loaded. |
| `SessionEnd` / `sessionEnd` | all | Drops state files idle for a week. It keeps the ending session's own: a resumed session keeps its id, and forgetting its loaded skills re-denied every skill rule after each resume. |

Codex runs the same command hooks (`.generated/codex/hooks.json`) with Claude's event names and payload; its shell tool arrives as `Bash`, its edits as `apply_patch`. The in-process harnesses map their own events:

| Guard step | opencode | pi |
|---|---|---|
| Shell guard, skill tracker | `tool.execute.before` (throw denies; ask is opencode's own prompt, from the `bash` ask entries the `config` hook appends) | `tool_call` (`{ block, reason }`; ask is `ctx.ui.confirm`) |
| Post-edit lint, pip note | `tool.execute.after` (appended to the output) | `tool_result` (appended to the content) |
| Typed `/skill` | `chat.message` | `input` |
| `make check` and result gate on stop | `session.idle`: on failure `client.session.prompt` (make check once, the gate at most twice per run) | `agent_settled`: on failure `pi.sendUserMessage` (the same) |
| Keep-awake, `guard.session` | `session.created` (`guard.session` for a root session only) | `session_start` (`guard.session` not in a subagent child) |
| State cleanup | `session.deleted` | `session_shutdown` |

## Decisions

- **Command hooks, not a mod or an extension.** Copilot CLI (1.0.95) loads a plugin's `hooks/hooks.json`, accepts Claude's PascalCase events and payload (`tool_name` carries Claude names such as `Bash`), runs `command` under bash or PowerShell, sets `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA`, and honours `hookSpecificOutput.permissionDecision` `allow|deny|ask`. One file serves every harness, with no `--experimental`.
- **VS Code reads the same file.** VS Code (1.139) detects the plugin as Claude format from `.claude-plugin/plugin.json`, loads `hooks/hooks.json`, maps both PascalCase and Copilot camelCase event names, sets `CLAUDE_PLUGIN_ROOT` but not `CLAUDE_PLUGIN_DATA` (state falls back to `<tmpdir>/guard-plugin-<uid>`, created `0700`), and **ignores `matcher`**: every command of an event runs, so each script checks `tool_name` itself and passes anything else untouched. VS Code sends its own tool names (`run_in_terminal`, `create_file`, ...) and reads `permissionDecision` and `additionalContext` from `hookSpecificOutput`. Its task tools run commands too, so the guard judges them as shell commands: `create_and_run_task` by `task.command` plus `task.args`, `run_task` by the command of the task its `id` (`type: label` or the label) names in `<workspaceFolder>/.vscode/tasks.json` (JSONC); a task it cannot read gets a note, not a decision. The field names come from VS Code's source and are not yet checked live ([#175](https://github.com/giocaizzi/harness/issues/175)).
- **One output, every reader.** Where the harnesses read different fields, the hook writes both: post-edit lint puts `additionalContext` at the top level (Copilot CLI) and in `hookSpecificOutput` (Claude, VS Code); the stop hook puts `decision`/`reason` at the top level (Claude, Copilot CLI) and in `hookSpecificOutput` (VS Code). Claude and Copilot CLI accept the extra fields (checked live); Codex does not, so on Codex (`--harness=codex`) the stop hook writes `decision`/`reason` only (checked by `make e2e`).
- **State in a file.** A command hook is a fresh process, so the loaded skills and the rules already reminded live in `$CLAUDE_PLUGIN_DATA/sessions/<session_id>.jsonl` as append-only facts, one JSON line each (`{"loaded":"ship"}`, `{"reminded":"edit","agent":"a1"}`). Each hook appends only its new facts in one `O_APPEND` write, which the OS keeps whole, so parallel hooks lose nothing and need no lock. Skill loads count for the whole session, subagents included; reminders count per agent, except the read and edit hints, which say the same thing to every agent and so come once per session. An event without a session id keeps nothing. How each harness names a subagent:
  - Claude Code and Codex send `agent_id` (and `agent_type`) from a subagent's hooks, with the parent's `session_id` (Codex 0.162.1, probed with `spawn_agent` against the e2e mock).
  - Copilot CLI sends `agent_id`, `agent_type` and `parent_agent_id`, with the subagent's own id as `session_id`; the guard files it under `parent_agent_id`, the parent session (Copilot CLI 1.0.98, probed offline against the e2e mock).
  - opencode runs a subagent in a child session (`parentID`): the adapter files it under the root session, as its own agent (probed: the child's calls land in the root session's file).
  - pi's dev-tools `subagent` tool starts a `pi -p --no-session` child with `GUARD_PARENT_SESSION` and `GUARD_AGENT_ID` in its environment, which the child's guard uses as its session and agent.
  - VS Code: not checked whether its hook input names a `runSubagent` subagent (no headless VS Code to probe); without an id its subagents share the main agent's reminders ([#172](https://github.com/giocaizzi/harness/issues/172)).
- **Remind once, ask every time.** A skill rule denies once per session with the skill to load; the title guard denies every time the subject of `git commit -m` (the first `-m` only; a `"$(cat <<'EOF' …)"` heredoc and `-F -`/`--file=-` with a heredoc are read), `gh pr create|edit --title`/`-t`, `glab mr create|update --title`/`-t` or `az repos pr create|update --title` does not match the org's PR-title check exactly (`^type(\(scope\))?!?: [a-z].*$`, scope `[a-z0-9._/-]`; az's `-t` is the target branch, so only `--title` counts). Every titled command in a chain or payload is checked, only at command position (`echo git commit -m x` sets none); a variable or a message file is unreadable and passes, and git's `Merge …` subjects are skipped; risky commands return `ask` every time, with a read-only blast-radius preview (`du -sh` of the delete's own targets, resolved through `cd`, `~` and variables; `git status --short`; `git log HEAD..@{u}`).
- **Hints for skills the agent misses.** A skill rule with `remind: true` (`pr-fix` on `gh pr view --comments`, PR comment API calls or `gh run view --log-failed`; `pytest` toward `python-testing`; `go test` toward `go-testing`; `go vet`, `go build` and `golangci-lint` toward `go-development`) and a `files` rule (an edit under `docs/` or to `README.md`/`AGENTS.md` toward `docs-sync`) add a once-per-session hint as `additionalContext` instead of denying. A whole command that only prints files (`cat f`, `head -n 5 f`, `sed -n 1,40p f`) gets a once-per-session hint toward the harness's read tool, except on Codex, which has none. Under Claude Code's auto mode, whose instructions tell the agent to read and make small edits through the shell, the read and edit hints are held back (not spent: they come once the session leaves auto mode). A shell file edit gets a once-per-session hint toward the edit tool, because the post-edit lint and the `files` hints run only on edit tools: `sed -i` (`-I`, `--in-place`), `perl -pi`/`-i`, inline Python (`-c`, a heredoc) with `open(…, 'w'|'a'|'x')` or `Path(…).write_text`/`write_bytes`/`open('w')`, inline Node (`-e`, `-p`, a heredoc, `deno eval`) with `writeFileSync`/`appendFile*`/`createWriteStream`, and `echo`, `printf`, `cat` (with a heredoc too), `tee`, `Set-Content`, `Add-Content`, `Out-File` into a file. A write to `/dev/*`, `$null`, an fd (`>&2`), stderr (`2>`) or a temp path (also through a literal path in the Python or Node call) is not an edit; other commands' output redirected to a file (`jq … > f`, `make test > log`) is left out, as tool output rather than hand-written content. Codex passes the hint on too, but has no read tool, so it gets no read hint ([compatibility.md](compatibility.md)). Each hint is logged as `guard.reminder`, so a miss is counted. Edits reach the hook because the `PreToolUse` matcher includes the edit tools.
- **Routing hint on subagent spawns.** Judgement work goes to `dev-tools:driver`, which carries its model and effort, and the hub often skips the `subagent-orchestration` skill that says so. So a spawn that bypasses the typed agents gets a once-per-session hint per case as `additionalContext`, never a deny (`rules.routing`, `evaluateRouting`): the built-in Plan agent (`routing-plan`: it runs on the session's model); an untyped spawn (`general-purpose`, `claude`, Copilot's `task`, Codex's `default`, or no type with a model) on a driver- or escalation-tier model (`opus`, `fable`, GPT Sol or Astra; `routing-model`); a named untyped spawn with no model, which runs on `CLAUDE_CODE_SUBAGENT_MODEL` or the session's model (`routing-untyped`: use `scout` for lookups, `worker` for routine edits, `driver` for judgement); and a typed agent (`dev-tools` `scout`, `worker`, `driver`, `reviewer`, `escalate`, `api:api-reviewer`, `factory:verifier`; a bare name matches too) spawned with a `model` or `effort`, which overrides its definition (`routing-override`). The values the routing tables allow pass: `factory:verifier` on Sonnet or Opus at `medium` or `high` (`ticket-run`), `dev-tools:reviewer` at `medium` or `high`, and on Opus only together with `effort: high` (a sensitive review, `subagent-orchestration`; the rule's `modelNeeds`): `model: opus` at `medium` or without an effort, or any other model, gets the hint. On Codex the worker registers as `dev-tools-worker`, and a bare `worker`, `default` or `explorer` on `spawn_agent` is Codex's built-in role, never ours. A spawn with no type and no model (a Codex fork, VS Code's copy of the current agent) gets nothing. The facts come from the spawn's input: Claude Code's `Agent` (`Task` before 2.1.63) `subagent_type`, `model` and `effort`; Copilot CLI's `task` and Codex's `spawn_agent` `agent_type` and `model`; VS Code's `runSubagent` `agentName` and `model` (from VS Code's source, `runSubagentTool.ts`; not checked live). Codex runs `PreToolUse` on `spawn_agent` and passes the hint to the model (`make e2e`, Codex 0.162.1); its `reasoning_effort` is ignored, since a Codex role's effort cannot be changed. No case can occur on opencode (its `task` carries no model, its generic agent `general` is not untyped here, and Plan is a primary agent) or pi (its `subagent` tool is not a spawn tool here and runs the session's model). Each hint is logged as `guard.reminder` with `cmd_class` `routing`.
- **Stacked-PR hint on `gh pr create` and `gh pr merge`.** Dependent work opened as a PR on the default branch carries the commits of the PR it builds on, so review and merge order go wrong. When the PR's head contains the head of another open PR of the user (`gh pr list --author @me --state open`, up to 10 checked: `git merge-base --is-ancestor origin/<other> HEAD`, or `origin/<head>` for a merge, and not yet in `origin/<default>`) and the PR targets the default branch (`--base` on create, `baseRefName` on merge), the agent gets a once-per-agent hint as `additionalContext`, never a deny or an ask (`rules.stack`, `stackTargets`, `stackFacts`, `evaluateCommand`): build it as a stack (`gh stack init`/`add`/`submit` where the repo has stacked PRs, merged bottom-up with `gh stack merge`), otherwise base the PR on the branch below (github-workflow, Stacks without `gh stack`). It comes after the skill rule, so the first `gh pr create` still gets the skill deny and the retry the hint. The lookups (the default branch from `origin/HEAD`, else `gh repo view`; the head; the PR list; two `merge-base` calls per candidate, in parallel) have their own 5 s budget (`STACK_MS`), which also bounds the hook: each call's timeout is the time left, and none starts after it; a `create` with `--head`/`-H` gets no hint. They run only on `gh pr create|merge` and only while the hint is unspent; any failure or odd branch name gives no hint. `GUARD_STACK_HINT=off` (`0`, `false`) switches it off and skips the lookups. Logged as `guard.reminder` with rule `stack`. One code path (`handle`), so every harness gets it.
- **Stale plugins.** A session keeps the plugin versions it loaded, so after an update it misses every fix until it reloads, and the user wants running sessions on the latest harness. Only the user can reload: `/reload-plugins` (Claude Code), `/restart` (Copilot CLI) and `/reload` (pi) are built-in commands the user types, which no tool reaches, and Codex, opencode and VS Code need a restart. So on a tool call without a decision the command hook compares this marketplace's installed plugin versions with the ones the session runs and, once per newer version, tells the user: "Harness plugins updated (guard 0.52.0 → 0.53.0): run `/reload-plugins` to load them." It goes out as the hook's `systemMessage` (Claude Code, Copilot CLI, VS Code's warning line), an opencode toast or a pi notification, and to the agent as context with "Only the user can do this: mention it to them once", which is the only channel `codex exec` shows (it prints no PreToolUse `systemMessage`; Codex's TUI not checked). What the session runs: in a versioned cache (`…/cache/<marketplace>/<plugin>/<version>`: Claude Code, Codex) guard's own path is exact; every other plugin, and every plugin of a dir updated in place (Copilot CLI, VS Code, the checkout opencode and pi run from), is recorded at the first tool call of each harness process (a command hook's parent process, checked stable over a whole run on Claude Code, Copilot CLI and Codex; the in-process harness itself; not checked on VS Code or Windows, where a shell between the harness and node would change it per call: a session file keeps at most four processes, so the note then stays silent and the file small), so a resumed or restarted session, a new process under the same session id, records what it loaded and is not told to reload. A reload inside the same process before the note shows (Claude Code's `/reload-plugins` with guard unchanged, Copilot CLI's `/restart`, pi's `/reload`) still gets one note per updated plugin. What is installed: Claude Code's `installed_plugins.json` beside the cache when it lists the plugin, its install for this session's scope (a project or local install whose project holds the directory the session started in, else the user one; another project's install does not count, nor does moving into one mid-session; paths compare with symlinks resolved, ignoring case on a case-insensitive volume), else the newest version dir (Codex, which also loads the newest dir at start), else each plugin's manifest. A note waits for the next call when the guard decides this one, is said once per session and version (subagents included), is logged as `guard.reminder` `rule=stale-plugins`, and anything unreadable reads as nothing newer (`hooks/stale.mjs`); a throw in the step leaves the call's decision standing. Never prune old version dirs from a plugin cache to tidy up: a running session pins its hook scripts at their exact versioned path, and removing it breaks that session's hooks (on Copilot CLI a failing `PreToolUse` hook denies every call).
- **Plain reads of project files never wait on a prompt.** A command that only prints files, `cat`, `head`, `tail`, `less`, `more` or `sed -n <line range>p` of plain relative paths (no leading `/` or `~`, no `:` or `\` (a Windows drive or PowerShell's `env:`), no `..`, `.` or empty segment; judged joined to the `cd` dir), optionally after one `cd <dir> &&` of the same form, with no quotes, variables, globs, redirections or pipes, gets `permissionDecision: allow` (with the read hint as `additionalContext` when due), so the harness's own permission prompt never stalls it (one such `sed -n` read sat 60 s unanswered overnight). A read outside the working tree (an absolute or home path, or a `cd` to one) gets no allow and goes through the harness's own permission flow, since a list of secret paths anywhere on disk cannot be complete. So does a relative read when the session's cwd is not inside a git work tree, or is in the home directory's own (`$HOME`, a dotfiles repo there): from `$HOME`, `cat .codex/auth.json` is a secret the path list may not know. Within the tree, a path that looks like a secret (`.env*`, `*.env`, `.git/config`, Terraform state and `*.tfvars`, `auth.json`, shell histories, `.netrc`, `.npmrc`, keys and certificates, `id_*`, names with secret, token, credential, passw or private, `.ssh/`, `.aws/`, `.gnupg/`, `.kube/`, `.docker/`, `.config/gh`, `.config/gcloud`, kubeconfigs) gets no allow either. Claude Code, Copilot CLI and VS Code honour the allow; Codex gets none (`--no-ask`: it has no prompt for this), opencode and pi ignore it.
- **Release rule and local tags.** The `release` skill rule (tags belong to release automation) leaves out `git tag -f <name> [<commit>]` and `git tag -d <name>…` when no remote has the tag: `git remote` lists none, or `git ls-remote --tags <remote> refs/tags/<name>` is empty for every remote (run in the command's repo, same budget as the other lookups; a failed lookup counts as on a remote). A tag named like a version (`v1.2.3`, `1.2`), creating a tag, an annotated or signed one, or any other release step in the same command still hits the rule, and so does a `git push`, `gh release` or a `gh api` write anywhere in the command (`-X POST|PATCH|PUT|DELETE`, `-f`/`-F`, `--input`, or `refs/tags` in sight, whatever the quoting: a ref can sit in a quoted field or an input file; `git tag -f foo && git push origin foo`).
- **Every spelling of a risky command, payloads included.** Rules match what runs, not text a command carries: quoted strings and heredoc bodies are blanked, so `rg -c 'rm -rf x' f`, `echo 'rm -rf /'` or a commit message naming a command pass. What runs although it is written as data is read again (`core/shell.mjs`) and judged by the same rules: the string after a shell's `-c` in any flag spelling (`bash -lc`, `sh -c --`, `$'…'` quoting, behind `sudo`, `env`, `xargs`), `eval`, `cmd /c`, `powershell`/`pwsh -Command`, a heredoc or `echo`/`printf`/`cat <<EOF` piped into a shell, `$(…)` and backticks even inside double quotes, `docker`/`podman`/`kubectl exec`, and `ssh`'s remote command, three levels deep. A wrapper that runs another command (`sudo`, `doas`, `env`, `command`, `exec`, `nohup`, `time`, `nice`, `timeout`, `xargs`, `caffeinate`, `stdbuf`, `ionice`, `chrt`, `taskset`, `setsid`, `unbuffer`, `watch`) is skipped with its own options (`WRAPPER_OPTIONS` in `core/shell.mjs`, from each tool's getopt string, the GNU, util-linux, BSD and macOS ones merged): a flag that takes no value skips one word and one that takes a value two, in a cluster (`sudo -nE`, `sudo -Eu root`), glued (`stdbuf -oL`), as `--name=value` or a unique long prefix, and past `--`; timeout's duration and taskset's mask sit before the command, chrt's priority only when the word is all digits (with a policy flag such as `-i` or `--other` the next word is the command), `time` before a group or `!` is the shell keyword, so the command inside is read (`time -p { …; }`, `time ! …`), sudo and env take `NAME=value` among their options, and the string `env -S` or `watch` (without `-x`) runs is read as a payload (#282). An option a wrapper's table does not know asks as `opaque`, since the command word may then be another one. Remote and container payloads get the local rules unchanged (owner decision D4): a remote `rm -rf /tmp/x` is a temp delete; but no fact about this machine (worktree, branch, git-ignored output) is gathered for another host's paths, so any other remote delete asks, naming the host. Heavy commands on another host do not trip the local host guard. What cannot be read asks as `opaque`: `-EncodedCommand`, `base64 -d`/`xxd -r`/`openssl -d` piped into a shell, payloads nested more than three levels. A pipe into a shell from anything else (`curl … | sh`) is not read and not asked about. Rules match with git's global options removed (`-C dir`, `-c k=v`, `--git-dir`, `--work-tree`, `--no-pager`, any combination), so `git -C x reset --hard` asks and `git -C x commit -m "bad"` is denied like the plain form; a relative target after `git -C dir` is judged as `dir/target`. A `.git` URL is not a git command (`git push https://h/r.git --force main` still asks). Recursive delete covers `\rm`, `command rm`, `/bin/rm`, `sudo rm`, `xargs rm`, `Remove-Item -r`/`-Rec`/`-Recurse:$true`, `ri`, `rd /s`, `rmdir /s`, `del /s`; `find` with `-delete` or `-exec`/`-execdir rm` asks too (find walks a whole tree, so any delete it runs is recursive). Git forms that lose work git cannot restore: `git clean -f` (not with `-n`/`--dry-run`), `git checkout`/`git restore` of the whole tree, a directory (`dir/`) or a glob (`.`, `:/`, `*.ts`; `restore --staged` alone only unstages) and `checkout -f`, `switch -f`/`--discard-changes`, `git stash drop`/`clear` (only `git fsck` finds the stash again), `git branch -D` (or `-d -f`; case-sensitive, since `-d` refuses an unmerged branch), `git rm -f` without `--cached`, `git push --mirror`/`--prune`, and `git push --delete`/`-d`/`:` of `main` or `master`. Left out, as recoverable or narrow: `git checkout -- f` and `git restore f` of one named file (a deliberate revert; asking each time teaches blind approval), `git rm` without `-f` and `git rm --cached` (the files are in git; `git rm -r` no longer asks as a recursive delete), `git push --delete` of another branch, `git stash pop` (keeps the stash on conflict), `git branch -d`, and aliases (`git co .`), which the hook cannot resolve. Codex and opencode prompt rules match from the first word, so a form with git's global options or a `find` delete is never a plain prefix there: they are denied with "ask the user to run it", as is `git push --delete main` (a prefix would also ask for every feature branch); `git clean -f…`, `git checkout .`, `git restore .`, `git stash drop`, `git branch -D`, `git rm -f`, `git push --mirror`/`--prune` have prefixes. Installing a new guard version needs `make install HARNESS=codex` again (the rules file changes; until then every risky command is denied on Codex, by design).
- **Data loss outside git (owner decision D3).** Asks: `docker`/`podman volume rm`/`prune`, `system prune`, container removal with its volumes (`docker rm -v`, `docker compose down -v`) (`docker`); `gh repo|release|secret delete` and `gh api -X DELETE` (`gh-delete`; a branch ref a merged PR holds passes, see Safe deletes); `kubectl … delete`, `helm uninstall`/`delete` (`k8s`); `gcloud … delete`, `az … delete` (`cloud-delete`); `dd … of=/dev/…`, `mkfs`, `diskutil erase…` (`disk`); `terraform`/`tofu apply`/`destroy`, global options such as `-chdir=` included (`terraform`). Git forms git cannot restore from the remote ask as `rewrite`: `git update-ref -d`, `git filter-repo`/`filter-branch`, `git branch -f main`. Left out on purpose: routine `docker rm`/`rmi` of disposable containers and images, `docker image prune`, `docker stack rm`, `chmod -R`, `rsync --delete`, a plain `git push origin feat:main` (the branch ruleset rejects it). `git reset --hard` asks wherever `--hard` sits (`git reset HEAD --hard`); a lease push naming main or master anywhere asks; `--force-if-includes` alone does not. Codex and opencode prompt for the plain forms (`docker volume rm`, `gh repo delete`, `kubectl delete`, `helm uninstall`, `tofu destroy`, `mkfs`, …); `gcloud`/`az` deletes have no first-word prefix and are denied there.
- **Safe deletes.** A delete with no target the hook can read (`xargs rm -rf`, `find -delete` without a start path) always asks, also next to a safe target. `rm -r`, `Remove-Item -Recurse`, `find -delete` (its start paths) and `git worktree remove --force` skip the ask when every target is strictly under a temp dir (`/tmp`, `/private/tmp` but not the tmux, X11 or ssh sockets there, the macOS per-user `/var/folders/<a>/<b>/T/`, a Windows user's `AppData\Local\Temp`, or the environment's own `TMPDIR`/`TEMP`/`TMP`), is git-ignored regenerable output, or is the root of a linked worktree that is clean, holds no git-ignored secret (`.env*`, `*secret*`, `*.key`: they exist nowhere else), and either has every commit on a remote ref or is squash-merged: `gh pr list --head <branch> --state merged` (run in the worktree, 5 s timeout) finds a merged PR whose head contains HEAD. Any gh failure asks, with the reason. Worktrees are checked in parallel. A `for VAR in w1 w2; do …; done` whose list holds only plain words is expanded once per word, so `for w in a b; do git worktree remove --force .claude/worktrees/$w; done` is judged per target; a list with globs, quotes or `$(…)`, a body that assigns or reads VAR, or a nested loop is not expanded and asks. A relative target after `cd DIR` (plain DIR, `;`/`&&` chains only) is checked as `DIR/target`, up to the first subshell, group, `||` or conditional in the command: a `cd` at or after one, a `pushd`/`popd`, a `cd` piped or sent to the background (`cd x | …`, `cd x &`, which change nothing after them; also with a newline after the operator) or any other `cd` makes later relative targets ask, and so does the first such construct after a followed `cd` (the `cd` may not have run). What runs before it keeps its directory, so `cd $S && rm -rf repo && git clone … ; (make test)` deletes `$S/repo` without asking. Within its `&&` chain a `cd` always holds (if it fails, nothing after it in the chain runs); past the end of the chain (`;`, a newline, `&`) it holds only when it surely ran: nothing but assignments and other such `cd`s ran before it in the whole command (so nothing could remove or move its directory first), and its directory exists when the hook runs (checked with `stat`, relative to the call's cwd). So `cd ~/repo && git pull; git branch -D feat` gets its branch facts in `~/repo`, while `cd /tmp/gone; rm -rf src`, `rm -rf x; cd x; rm -rf src` and `[ -d x ] && cd x; rm -rf src` ask: there the shell would delete `./src`. Paths resolve the way the shell would, by position (owner decision D5): a leading `~` or `$HOME` from the hook's environment (`USERPROFILE` on Windows), in `cd`, `git -C` and the targets alike, `$PWD` from the absolute directory a followed `cd` reached (`cd $S && D=$PWD/data && rm -rf $D`; a `cd` drops any `PWD=` assignment, as bash does), and `$NAME` from an assignment earlier in the same command (`NAME=/abs/path`, `NAME=$(mktemp -d)`, `export NAME=…`; the latest wins, and a non-path value forgets it). A prefix assignment (`NAME=/tmp/x cmd && rm -rf $NAME`) holds for that one command, so it is not followed, and neither is an assignment after the delete, inside `echo`, or a variable from the environment: those ask, as do `~user`, globs outside a temp dir, `..` and quotes. A payload whose text this shell expands before it runs (`bash -c "…"` or `eval` with a `$` outside single quotes, an `ssh` command line, a heredoc or `echo` piped into a shell) resolves `$NAME` and `$PWD` with the values outside it, never its own assignments and `cd`s: in `bash -c "cd /tmp/x && rm -rf $PWD"` the shell substitutes the caller's directory first, so it asks. A payload that also escapes a `\$` or a backtick for its own shell (`bash -c "D=x; rm -rf \$D"`, a heredoc or `echo` with `\$`) resolves no variable and no `$PWD`, since either level's value could apply: its variable targets ask. A single-quoted `-c` payload and a `$(…)` resolve their own. So `cd ~/repo && git branch -D feat` gets its branch facts in `~/repo`, and `SP=/private/tmp/x; cd $SP && rm -rf out` is a temp delete. The pip deny is judged in the repo the command runs in (`cd <uv repo> && pip install x`), and the edit hint ignores writes to a temp dir reached through `cd` or a variable, and `sed -i`/`perl -pi` of temp files. Regenerable output: the last path segment is one of `node_modules`, `.venv`, `venv`, `__pycache__`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`, `.terraform`, `dist`, `build`, `.next`, `target`, `coverage`, `.turbo`, `.cache`, `.wrangler`, `.vitest-cache`, `.vite`, `.gradle`, `.parcel-cache`, `.svelte-kit`, `.nuxt`, or `results` under `evals/` (not `out`: a source folder in some stacks); no segment looks like a secret (`.env*`, `*secret*`, `*.key`); and `git -C <parent> check-ignore -q -- <name>` succeeds, which also proves it is inside a repo and untracked (tracked files under it are in git anyway). A glob, an unresolved `cd` or a check that fails asks. `git branch -D` skips the ask when every branch it names has no commit off the remote refs (`git rev-list --count <b> --not --remotes` is 0) or its tip is in the head of a merged PR of that name (squash merge, remote branch deleted; the same `gh` check as worktrees); otherwise the ask says why per branch. A branch delete in an `ssh` or container payload never rides on a safe local one. `gh api -X DELETE repos/<owner>/<repo>/git/refs/heads/<b>` (also `{owner}/{repo}`, which gh fills from the repo the command runs in) skips the ask when the ref's tip (`gh api repos/<o>/<r>/git/ref/heads/<b>`) is the head of a merged PR of that branch (`gh pr list -R <o>/<r> --head <b> --state merged`), so the merge holds every commit the ref has. The endpoint is gh's first operand, with every option's value skipped, so a `--jq` or `--template` value naming a ref is not taken for it. `main`, `master`, a tag, a ref the guard cannot name, `--hostname`, a `GH_REPO` or `GH_HOST` set in the command, a gh failure or any other GitHub delete in the same command asks. `git push origin --delete <b>` of a feature branch never asked (only `main`/`master` do). Post-merge cleanup chains (`cd <repo> && git pull --ff-only && git worktree remove <wt> && git branch -D <b>; git worktree prune`) therefore run without asking in any mode once the PR is merged, however long the chain: the split deny below applies only to a step the guard could not prove safe.
- **Readable asks.** An ask (and a deny the agent reads) starts with what the risky part does in plain words, with the targets the guard resolved: `Risky command: Deletes 2 paths recursively: sub/build, sub/dist.` (after `cd sub`), `Force-pushes origin feat.`, `Deletes branches a, b.`, `… on pi.local.` for an ssh payload; then `Step:` the risky pipeline on its own when the command has more than that; then `Rule:` the rule id and why; then the facts that made it ask (`Worktree x: 2 unpushed commits`). A risky step buried in a long command is denied instead, with "Run the risky step as its own simple command … Then retry": when the whole command chains more than 3 commands, or when the step sits in a `bash -c`, `eval` or `ssh` payload next to 2 or more other commands (owner decision D15). A shorter chain just asks. Logged as `guard.decision` with `via=split`.
- **Secret reads ask, injection passes.** Two risky rules ask every time, with a reason naming the `secrets-handling` skill: `secrets` (`bw`/`bws` `get`, `list`, `run`, `unlock`, `login`, `export`, `serve`, `bws secret`; `security find-generic-password`/`find-internet-password` with `-w` or `-g`; `chezmoi secret keyring get`; `op read`, `op item get --reveal`; `pass show`; `gcloud secrets versions access`; `az keyvault secret show`; `printenv` of a TOKEN, SECRET, KEY, PASS or CREDENTIAL name; the CLIs' own token printers, `gh auth token`, `gh auth status --show-token`, `gcloud auth print-access-token`/`print-identity-token`, `az account get-access-token`; `security dump-keychain`; a bare `env` or `printenv` dump, alone or piped to anything but a filter (owner decision D9); any reader (`cat`, `less`, `head`, `tail`, `bat`, `grep`, `rg`, `sed`, `awk`, `cut`, `jq`, `source`, `.`, a `<` redirect) of a `.env`, `.env.<name>` or `.envrc` file (`.env.example`/`.sample`/`.template`/`.dist` excepted, also when quoted: `cat ".env"`), `~/.netrc`, `~/.aws/credentials` or a private `~/.ssh/id_*` key (not `.pub`); and `echo`, `printf` or `Write-Output` of a variable named `*_TOKEN`, `*_KEY`, `*_SECRET` or `*PASSWORD`, quoted or not (`$KEY_PATH` passes)) and `secrets-env` (`printenv` or `env` piped to `grep`, `rg`, `findstr` or `Select-String` when that pipeline names TOKEN, SECRET, KEY, PASS, CREDENTIAL, TOK, GH_, PAT or BEARER; its `raw` pattern reads the pipeline as written, since the grep pattern is usually quoted, and only that pipeline, so a secret word elsewhere in the command does not count; a pipeline that ends keeping only the names, `cut -d= -f1`, `sed 's/=.*//'` or `awk -F= '{print $1}'`, prints no value and passes). `printenv <name>` of another variable and `env | grep PATH` pass. An ask, not a deny: reading a secret is often the task, and the user decides. A secret CLI asked only for its usage passes: `bw`, `bws`, `op`, `pass`, `security`, `chezmoi`, `gcloud`, `az`, `gh` or `printenv` ending in `--help` or `-h` that does not follow another option (where it could be that option's value: `gh auth token --hostname --help` asks), or with a `help` subcommand (`bws secret get --help | head`, `op help read`). A file reader never passes this way (BSD `cat .env --help` prints the file). The rule is judged per pipeline, so `bws secret get x | grep --help` still asks. A token injected for one command, `VAR="$(<keyring read>)" ./script` (also `export VAR="$(…)"`, also inside `bash -c`), passes without asking: the secret rules (`skipInjected`) do not look inside a double-quoted `$(…)` that is the whole value of an assignment, since the value goes to an environment, never to output, which is what `secrets-handling` prescribes; asking there would teach the user to approve blindly. Every other rule still reads it (`x="$(rm -rf src)"` asks). Unquoted, `VAR=$(...)` asks, and so does `echo "$(bws secret get x)"`. `bws run -- <cmd>` asks: it hands every project secret to a command the hook cannot vet. Codex and opencode prompt for the plain forms in the rule's `prefixes` (also `gh auth token`, `gcloud auth print-access-token`, `az account get-access-token`, `security dump-keychain`); `security find-…-password`, `op item get --reveal`, `printenv`, a bare `env`, the `env` pipes and echoed secret variables are denied there with "ask the user to run it". These replace the old `secrets` skill reminder.
- **Fail open for reminders, closed for risky.** A crash while judging a risky command denies it; anything else lets the call through. The script never exits non-zero, because Copilot denies a `preToolUse` whose hook fails. A hook timeout would fail open (Claude Code and VS Code fall back to their normal permission flow, so a bypass-mode session runs the command; Copilot runs it; Codex continues), so the hook keeps its own budget under the 30 s limit (owner decision D2): the slow lookups (worktrees, branches and PRs, ignored build output) get 20 s and the blast-radius preview 3 s. A lookup that runs out is dropped and the fast rules still apply, so a delete that could have been shown safe asks, saying "Checks unfinished"; nothing fails open. Telemetry is sent without holding the decision back. On Codex the rollout is read only on an ask, and only its last 256 KB: an older `turn_context` counts as no record and denies. Without `node` on PATH no hook runs: Claude Code, VS Code and Codex run the command (fail open), Copilot denies it (fail closed, owner decision D11; [#174](https://github.com/giocaizzi/harness/issues/174)).
- **Deny rules are data, scoped to the repo.** `rules.deny` (pip, pipx, `python -m pip`; poetry) is matched on what the command would run, so a quoted mention passes. pip is denied only at command position (owner decision D13): `pip install|uninstall|download|wheel` (also `sudo pip3`, `.venv/bin/pip`, `python3 -mpip`), `pipx install|run|inject|upgrade|reinstall`; `which pip`, `git log --grep pip`, `echo pip install`, `uv pip …` and read-only `pip list`/`pip freeze` pass. A rule with `when: "uv"` denies every time, before anything else, only in a uv repo; elsewhere the command runs and the agent gets one note per session (`hookSpecificOutput.additionalContext`, no permission decision) naming the repo's manager. Copilot CLI (1.0.95) passes that note to the agent too (checked live), and VS Code documents `additionalContext` on `PreToolUse`. The hook finds the manager in the nearest directory up to the repo root: `uv.lock` → uv; `poetry.lock` or `[tool.poetry]` → poetry; `Pipfile`/`Pipfile.lock` → pipenv; `requirements*.txt` without a `pyproject.toml` `[project]` table → pip; any other `pyproject.toml` → uv; none → no Python project. Plain `node:fs` calls, the same on every OS; a read error counts as no project.
- **No self-approval in a factory run (owner decision D16).** While `FACTORY_RUN_ID` is set, the guard fails closed on the factory approval label (`factory-approval`, `Rule: rules.factory`), without a shell tokenizer. A command that names the label (a whole word, in any quoting or case, across a line continuation: `agent-o'k'`, `Agent-OK`, `-lagent-ok`, `agent-o\⏎k`) is denied unless it is one plain `gh` read. Plain means: single-quoted spans removed (they are literal), double-quoted spans removed when they hold no `\`, `$` or backtick, `{name}` braces (one name, no `,` or `..`) kept as literal, and nothing left of `; & | < > ( ) { } $` backtick `\ # * ? [ ] ' "` or a newline; then `gh` is the first word, with no assignment or wrapper before it. A read is `gh issue|pr view|list|status` without `--web`, or `gh api <path>` with no `-X`/`--method` but GET, no `-f`/`-F`/`--field`/`--raw-field`/`--input` in any pflag spelling (`-f=k=v`, `-fk=v`, `-XPOST`) and no flag `gh api` does not know. So `gh issue list --label agent-ok` and the gate's `gh api …/timeline --jq '… "agent-ok" …'` pass, and a skill that needs to filter output uses `gh`'s own `--jq`. Everything else that names the label is denied, adding and removing alike (in a run the agent never touches the label), and so is a read that is piped, chained, substituted, redirected, wrapped or behind a prefix (`L=$(gh issue list --label agent-ok)`, `gh issue list --label agent-ok | jq …`, `grep agent-ok f`). A `gh` command that sends a body the guard cannot read (`--input`, a `key=@file` field) is denied even without the label in sight, unless it is one plain `gh api` call writing to a `/comments` endpoint or a literal path outside `/labels` and `/issues` (so editing a factory comment with `-F body=@file` passes). Any other line that runs `gh api`, or a `gh` whose subcommand is not a literal word (`gh $'a'pi`, `gh "$X"`, `gh>/dev/null api`, zsh `=gh api`, `gh` as a parameter expansion's value or default), or a Windows path to `gh.exe` written with backslashes, is denied too, label or not, since the shell can rebuild `--input` or `=@` from an expansion (`--in$'p'ut`), unless the shell reader splits the line cleanly, each such `gh` is a plain read of its own at the top level (so an alias or extension, `gh <name>`, or a `gh api` write does not pass), and those reads account for every such `gh` in the line's text (`echo …; gh api user --jq .login; git remote -v | head -2` passes; one in a substitution, behind `xargs`, with a built subcommand or in a heredoc body, which a later `bash x.sh` may run, does not; a line that defines `gh` as a function or alias never passes; a body flag anywhere in the line still denies); a `gh issue|pr|repo|run|…` line keeps its pipes, chains and substitutions (`git push && gh pr create …`, `URL=$(gh pr create …)`). A plain `gh <name>` whose name is not one of gh's own commands (`rules.factory.ghCommands`) is an alias or extension, which can run any command out of sight, so it is denied in a run (`stack`, an extension, and `co`, an alias gh stores in the user's config, included; write `gh pr checkout`), as is `gh copilot`, which starts an agent the guard never sees, and so are `gh alias set|import` and `gh extension install|upgrade|remove|exec` (also `ext`, `extensions`), which make, swap or run one (#273). The list is gh 2.102's commands, their aliases and help topics: a newer built-in is denied until it is listed, and on an older gh a name that is a built-in only in a later release may be an extension the list lets through. Such a non-plain line that carries the word `gh` followed by anything but a subcommand, even in prose (`git commit -m "see gh CLI" && …`), is denied: put the text in a file. This is defense in depth, not the trust boundary: whatever the guard cannot read as plain ends in a deny, never an allow. Denied on purpose, as text that names the label: a comment or commit message that mentions it (`gh issue comment N --body "… agent-ok …"`, `git commit -m "… agent-ok …"`), a GET search with `-f q=label:agent-ok`, and `gh api -X DELETE …/labels/agent-ok`. Leave the label's name out of such text, or put it in a file and use `--body-file`. The label is `labels.approval` of the nearest `.factory/config.yaml` above the call's cwd, else `agent-ok`; names compare ignoring case. A config that exists but cannot be read, or whose `labels` cannot be parsed (flow style, a key without a plain value), fails closed (`factory-config`): every command that may change a label (it mentions `label`, or a `gh`, `hub` or `glab` line passes `-l`) is denied unless it is one plain `gh` read. So is a `gh issue|pr create|edit` whose flags the text cannot show, read with the shell reader (which decodes `$'…'` and joins line continuations): a subcommand that is not a literal word (`gh issue $E`, `gh issue e$'d'it`), a flag name that expands or globs (`--add-${A}el`, `--add-lab{e,}l`), a whole word that expands where no value-taking flag precedes it (`"$F"`, `--draft "$F"`; the booleans `-d`, `--draft`, `--dry-run`, `-f`, `--fill*`, `--no-maintainer-edit`, `-w`, `--web`, `-e`, `--editor` take none), an unquoted expansion anywhere, which the shell splits into more words (`-b $F`, `--body=$F`), or arguments xargs adds. Quoted values pass (`-b "$(cat body.md)"`, `--body-file "$TMPDIR/b.md"`), so does a gh command that cannot add labels (`gh pr view $N`), and the deny reason asks for literal flags, quoted values and a literal `--body-file` path. Denied on purpose there: an issue or PR number from a variable on `create|edit` (`gh issue edit $N …`), since the word could be a flag. Any command naming a label the guard could still find in the file is denied too. Not seen: a run that renames the label in the config with a file-edit tool before touching it; the config is read again at each command. Without a run the command passes. A command word, at any depth, that the shell may resolve to `gh` without spelling it is denied in a run too: another letter case (`GH`, which macOS and Windows find), an ANSI-C string, a trailing dot (which Windows drops), or a glob or brace list that could match `gh` or `gh.exe`, a POSIX bracket class (`[[:alpha:]]`) or a word over 256 characters counting as a match (#274). Every word up to the command is read, past reserved words (`then`, `{`, `!`, `coproc`, a named coprocess, a function body), and behind a known wrapper only the words at command position are read, each wrapper's options skipped with its own table (`sudo -E -u x …`, `timeout -s KILL 5 nice …`, `stdbuf -oL …`; #282), so an option value or an argument that looks like `gh` passes (`env -u GH ls`, `timeout 5 ls *`). A unit with a wrapper option the table does not know is read whole, so a value there that may name `gh` is denied (fail closed). Not seen (known best-effort bypasses): a label the shell builds and the line never spells (`L=agent; gh issue edit 7 --add-label $L-ok`, `agent$'\x2d'ok`), a label spelled in an encoding the server decodes (`…/labels/agent%2Dok`), `gh` run under a name the shell builds (`$GH`) or through a function or alias defined outside the line, `gh` in another case or as a glob behind a wrapper the reader does not know (`busybox`, `chronic`), zsh options that turn plain words into globs or lists (`extendedglob` `^x`/`~x`, `braceccl` `{name}`) when a planted file supplies the flag, a write that names the label by id instead of by name (a GraphQL `addLabelsToLabelable` with the label's node id), and a write that never names the label in the command line, such as a script. The runtime cannot tell the agent's label from the owner's when the run's token is an approver (the timeline shows the approver), so this deny is the only barrier besides the untrusted-data rule; the real fix is a dedicated bot or App identity that is not an approver (the runtime adds a `doctor` warning). The takeover label (`labels.takeover`, else `factory-takeover`; rule `factory-takeover`, `Rule: rules.factory`) gets the same check, so a runtime run never applies or removes the label an approver uses to hand its ticket to an attended run ([factory.md](factory.md#takeover)). One code path (`handle`), so every harness gets it.
- **No protected-path writes in a factory run (#213).** While `FACTORY_RUN_ID` is set, a shell write to a protected path is denied (rule `protected-path`), logged to the factory events file like any deny, so the factory runtime can count it toward its protected-paths breaker. Protected are `.github/**` and `.factory/**` always (`rules.factory.protectedPaths`), plus the globs in `FACTORY_PROTECTED_PATHS`, one per line, which the runtime sets for a run. The list is additive: the variable only adds globs and never replaces the two defaults, and unset or set but empty both mean the defaults alone. One exemption narrows the defaults: a file inside a run directory, `.factory/runs/*/*/**` (`rules.factory.exemptPaths`; the run's own outputs `result.json`, `checklist.md`, `verdict-<round>.md`), is not protected, while `.factory/config.yaml`, every other `.factory/` path, the runs directory itself and a run directory itself (`.factory/runs`, `.factory/runs/12`: writing, `rm -r`, `mv` away) stay so (#302). The path is normalised first and then tested, so `.factory/runs/../config.yaml` and `.factory/runs/x/../../config.yaml` are `.factory/config.yaml`; the exemption holds in the spellings the rule reads (relative, absolute, `./`, the redirect and every writer below, and a leading substitution or variable that the reader drops, such as `$(git rev-parse --git-common-dir)/../.factory/runs/12/verdict-1.md`), but only for a path spelled out in full: a wildcard, variable, brace list or `~` after that start (`.factory/runs/$N/x`, `.factory/runs/*/x`) is not waived, since it could stand for `..` or the config, and neither is a segment ending in a dot or a space (Windows strips them, so `12\.. ` is `12\..`); such a write is denied like before. Only a substitution without nesting and without a `/` inside is understood as a start: `$(dirname "$(git rev-parse …)")/.factory/runs/12/x` and `$(git -C /r rev-parse …)/…` stay denied (known over-deny); spell the path as a literal absolute path or as `$(git rev-parse --path-format=absolute --git-common-dir)/../.factory/runs/12/x`. An explicit glob in `FACTORY_PROTECTED_PATHS` always wins over the exemption: listing `.factory/runs/*/result.json` (or `.factory/**`) protects it. A glob is over paths relative to the repo root (the nearest directory above the call's cwd holding `.git`, a file in a worktree or a submodule, else the cwd): `**` spans directories, `*`, `?` and `[…]` stay within one, and a trailing `/` means the whole directory (`infra/` is `infra/**`). Letter case is ignored, as macOS and Windows resolve paths, and a Windows path's backslashes count as separators. A write is an output redirection of any command (`>`, `>>`, `>|`, `&>`, `&>>`; `>&2` duplicates a descriptor and is not one), `tee`, `sed -i` and `perl -pi`, `Set-Content`, `Add-Content`, `Out-File` and `Tee-Object`, the operands of `rm`, `rmdir`, `unlink` and `Remove-Item` (and its aliases), the sources and destination of `mv` and `Move-Item`, and the destination of `cp` and `Copy-Item` (`-t`, also at the end of a short-flag cluster (`-rt DIR`) or with its value glued, `--target-directory` or a prefix of it (`--target=`), `-Destination`, else the last operand; cp's `-T` takes none; the destination is also read as `<dest>/<source name>`, since it may be a directory); at any depth (`bash -c`, `$(…)`), past reserved words (`then`, `else`, `do`, `{`, `!`, `coproc`, a function body) and known wrappers (`sudo`, `timeout`, …), in the directory a followed `cd` reached (an absolute target stays where it says), with `~`, `$HOME` and the absolute or temp-dir values the command assigns resolved. Deleting or moving away a directory above a protected path counts too (`rm -rf .github`, `rm -rf .`), along a glob's literal leading segments only: `**/*.tf` puts no directory above it, so `rm -rf dist` passes even if it holds `.tf` files. A target the shell globs is matched as a glob (`.g*` may name `.github`; a leading `*` or `?` never names a dot file, so `rm -f *.tmp` passes; `*.log` never meets `*.tf`), a brace list is expanded (innermost list first, a range kept as a glob, a group that is no list left as written), and a target whose start the guard cannot know (a variable it did not resolve, `~user`, a `cd` it does not follow) is matched by the rest of its path anywhere (`$ROOT/.github/x` denies, `$TMPDIR/x` passes; a variable glued to a name may be empty, so `$P.github/x` denies too; after such a `cd` only what the target spells counts, so `rm CODEOWNERS` there passes). Reading, and copying a protected file out, pass. It fails closed for a command that may write (an output redirection, or one of the writers above): past 512 write targets in one command (each operand counted once), 1024 characters in a target, 64 words or groups in one brace list, or 2 s of checking (`rules.factory.protectedLimits`), or if the check itself fails, the command is denied, since a hook that times out or emits nothing lets the command through; the deny says to split the command. A command that writes nothing (`ls`, `git status`, `printf` with a long brace list) passes whatever its size. The setting is cut, not failed: a glob over 1024 characters is ignored, and so is every glob past the first 256, the two defaults counted first, so a list too long protects only its first 254 added globs. Not seen (best effort, the forge diff stays the runtime's other signal): a path built wholly from a variable (`> "$F"`, `$D/x` with a relative `D`), targets fed by `xargs` or `find -exec`/`-delete` (`grep -rl x | xargs sed -i …`), wrappers the reader does not know (`busybox`, `chronic`), `cmd /c`, any other writer (`install`, `ln`, `touch`, `dd`, `truncate`, `mkdir`, `New-Item`, `curl -o`, `wget -O`, `tar -C`, `unzip -d`, `rsync`, `patch`, `git mv`, `git rm`, `git checkout`, `git restore`, `git apply`, an interpreter's file API, a script), an encoded command, and edits through the harness's edit and write tools (a follow-up, #281). Root edge cases, best effort: in a submodule the submodule is the root, so the superproject's paths count as outside; with the cwd outside any repo the cwd is the root, so `<repo>/.github/…` passes; the repo reached through its parent (`../<repo name>/…`) and a sibling worktree of the same repo count as outside. The check runs in `handle` on the shell path, one code path for every harness (Claude Code, Copilot CLI, VS Code, Codex, opencode and pi).
- **A factory run cannot end without a valid result file (#306).** Before `make check`, the stop hook's result gate checks the run's `result.json` with the `factory` plugin's own checker (`check-result.mjs`, copied into `.generated/factory/` by `make build`, so guard runs it without importing across plugins). It applies only in a factory run. A runtime's run (`FACTORY_RUN_ID` and `FACTORY_TICKET` set) is blocked while `<main checkout>/.factory/runs/<n>/result.json` (the main checkout is the parent of `git rev-parse --git-common-dir`, `<n>` the ticket number) is missing, is not JSON, fails a check, or carries another run's `run_id` (the checker compares it with `FACTORY_RUN_ID`). In a group run (`FACTORY_RUN_FILE` set), the checker also requires `tasks` to list the run file's members, exactly and in order, and blocks on a run file it cannot read; the gate resolves a relative `FACTORY_RUN_FILE` against the session's `cwd`, while `write-result.mjs` resolves it against its own working directory, so the run calls it from the session directory. An attended run (`FACTORY_ATTENDED_RUN_ID` and `FACTORY_ATTENDED_TICKET`, set by `ticket-run`'s launcher) is blocked only by a file that carries its own `run_id` and fails a check: a missing file, broken JSON or another run's file pass, since an attended run that stops at the gate writes nothing. The block lists the checker's errors (capped at 50 lines) and says to write the file with `ticket-run`'s `scripts/write-result.mjs`, never by hand. It blocks at most twice per run id (a counter under `result-gate/` in the plugin data dir), then lets the run end, so a run that cannot write a valid file still stops; it ignores `stop_hook_active`, which only skips `make check`. When `make check` also fails, one block carries both reasons, the gate's first. It never applies to a subagent's stop (a payload with `agent_id`, or a `SubagentStop`; pi's `subagent` tool starts its child with `GUARD_RESULT_GATE=off`), and it fails open: outside a git checkout, with a malformed ticket or on any error of its own, the agent stops. `GUARD_RESULT_GATE=off` turns it off, as a separate verifier session of a factory run does. The block text tells a subagent to ignore it and end its turn. Gap on Codex ([compatibility.md](compatibility.md#matrix)): its `Stop` payload does not mark a subagent's stop, and there the verifier runs as a subagent before the record step, so `result.json` is normally still missing when it stops. If Codex fires `Stop` for subagents, the verifier uses up both blocks and the main session's stop then passes: the gate in practice does not hold a Codex run that has a verifier, which is every run past the plan. opencode and pi cannot block a stop: the reason is sent back as a new message, as for `make check`.
- **A clean first turn or docs-only change runs no stop check.** The changed paths are `git diff --name-only --no-renames` against the last green run's `HEAD` (against `HEAD` when there is none, as in a new worktree) plus untracked files, from the repo root; diffing against the green run's commit means a code commit since then still runs the check, and `--no-renames` lists a code file moved into `docs/` as its deletion too. The check is skipped when there are no paths, or when every path is docs by the rules in `core/docsonly.mjs`, and nothing is marked green. The default list, gitignore-style (a pattern without `/` matches the file name at any depth, one with `/` is anchored at the root, matching ignores case and reads `\` as `/`): `README*`, `CHANGELOG*`, `LICENSE*`, `CONTRIBUTING*`, `CODE_OF_CONDUCT*`, `SECURITY*`, `docs/**`, `*.md`, `*.mdx`, `*.txt`, `*.rst`, `*.adoc`, images (`png`, `jpg`, `jpeg`, `gif`, `svg`, `webp`, `ico`), `pdf`, `mp4`, `mov`, `woff`, `woff2`, `ai`, `psd`, `NOTICE*`, `AUTHORS*`, `CODEOWNERS`, `CITATION.cff`, `.github/ISSUE_TEMPLATE/**`, `.github/PULL_REQUEST_TEMPLATE*`, `.github/FUNDING.yml`, `.editorconfig`, `.vscode/**`, `.idea/**`, `.DS_Store`. Never skipped by default, even inside `docs/` or as `.txt`: `json`, `yaml`, `yml`, `toml`, `.gitignore`, `.env.example`, lockfiles (`*.lock`, `*.lockb`, `go.sum`; `package-lock.json` and `pnpm-lock.yaml` by type), `Makefile` and `*.mk`, `ipynb`, data files (`csv`, `tsv`, `parquet`, `xml`, `sql`, `snap`), `fixtures/`, `testdata/`, `__snapshots__/` and `golden/` at any depth, `requirements*.txt`, `constraints*.txt`, `CMakeLists.txt`, `.github/workflows/**`, `.github/dependabot.yml`; the `.github` templates and funding file and the editor directories above are the exceptions, docs whatever their type. `GUARD_STOP_CHECK=off` disables checks; `force` retains the docs-only skip but runs an explicitly requested check on a clean tree.
- **A repo tunes the skip list in `.stop-check-ignore`.** A file at the repo root, one gitignore-style pattern per line, `#` for a comment, appended after the defaults with the last match winning: `!pattern` keeps matching paths checked (Markdown that `make check` validates), a plain `pattern` makes more paths skippable. This repo's keeps `plugins/**`, `.agents/**`, `tests/**` and `README.md` checked, since `make validate` reads skills, agents and the READMEs' tables. A file, not a Makefile variable: the hook reads it with one `readFileSync` and needs no make to evaluate it (a variable can come from an include, `+=` or a continued line, which only `make` itself resolves); a repo of any build tool can have one; and its syntax is the one `.gitignore` already teaches. Example for `acme/app`, whose `make check` lints its Markdown and that publishes `site/`: `!*.md` and `site/**`.
- **Stop runs `make check-fast` or `make check` once, and only on change.** A repo whose full check is slow defines `check-fast` (lint, types, quick tests) and the hook runs that; otherwise it runs `check`, and CI keeps the full suite either way. No make, no Makefile or neither target: the agent stops. The hook fingerprints the repo (`HEAD`, `git diff HEAD`, untracked files' names and contents through `git hash-object`; past 2,000 untracked files it always runs) and skips the check when it equals the last green run, stored under `$CLAUDE_PLUGIN_DATA/stop/` with that run's `HEAD`; outside git it always runs. It also skips a docs-only change (next decision). A failure blocks the stop with the last 40 lines; the next stop (`stop_hook_active`) always passes, so it cannot loop (Copilot also caps at 8 blocks). make runs detached from the terminal (owner decision D7): stdin closed, output piped, its own session (`setsid` on Unix), `CI=1`, `TERM=dumb`, so a recipe that reads `/dev/tty` fails at once instead of hanging the session; opencode and pi run it async, so their event loop keeps going. The check is killed with its whole process group after 300 s (`GUARD_STOP_TIMEOUT_MS` overrides; the hook limit is 1800 s), and the hook returns at once without waiting for the output pipes to close: a grandchild outside the group (an MSYS `&` job on Windows, which `taskkill /T` misses) can hold them open. The check never becomes the bottleneck: past the timeout, on a strained host (the guard's `host` caps: load or free disk) or while another stop check runs in the same repo (a pid lock under `stop/`; a dead holder's lock is removed and taken again exclusively, so only one stop wins), it is deferred with a `systemMessage`, never blocks and nothing is marked green, so the next stop runs it. A subagent's stop runs no check, its parent's does: opencode skips a session with a `parentID`, and pi's `subagent` tool starts its child with `GUARD_STOP_CHECK=off`. `GUARD_STOP_CHECK=off` disables the hook; `GUARD_STOP_CHECK=force` skips the host-strain deferral (the lock and timeout still apply), for CI runners whose load sits above the cap by design, such as the e2e's macOS runner.
- **Lint is advice, not a block.** Findings come back as `hookSpecificOutput.additionalContext`; a missing shellcheck, pwsh or PSScriptAnalyzer skips silently. The file path is `tool_input.file_path` (Claude), `tool_input.path` (Copilot), `filePath` or `replacements[].filePath` (VS Code), or the `*** Add/Update File:` lines of an apply_patch (the whole `tool_input` on Copilot, `input` on VS Code, `command` on Codex). A `.sh` whose shebang is not sh, bash, dash or ksh (zsh, fish) is skipped, since shellcheck cannot read it, and so is any file in a temp dir: scratch files are not the repo's to fix.
- **Keep-awake follows the harness.** The hook walks past shell parents to the harness pid (under VS Code, the extension host: the keeper lives as long as the window) and starts a detached keeper bound to it: `caffeinate -i -w <pid>` (macOS), `systemd-inhibit --what=idle:sleep tail --pid=<pid> -f /dev/null` (Linux), a hidden PowerShell holding `SetThreadExecutionState(ES_CONTINUOUS|ES_SYSTEM_REQUIRED)` until `Wait-Process -Id <pid>` (Windows). The keeper pid is kept in `$CLAUDE_PLUGIN_DATA/awake/<harness pid>.pid`, so resume, `/clear` and compaction reuse it. It prevents idle sleep only; the display may still sleep.
- **Codex: generated hooks file, prompt rules for the ask.** Codex rejects a hooks file with the Claude-only `modules` key and does not support `ask` (it marks the hook failed and runs the command). `build_agents.mjs` writes `.generated/codex/hooks.json` without `modules`, with `--no-ask` on the guard command. With `--no-ask` a risky command of single-spaced plain words (no `$`, `~`, globs, quotes, escapes or operators, which Codex does not parse and so runs without its prompt rules) starting with a rule's `prefixes` passes the hook, and Codex's own prompt rule asks. It does so only when `$CODEX_HOME/rules/giocaizzi-guard.rules` equals this version's `codexRules`, so a stale or missing file never lets a command through unasked, and only when the session's last `turn_context` in the rollout (`transcript_path`) has `approvals_reviewer` `"user"`: that is the effective value from config, profiles, `-c` and `--approve-for-me`, and an AI reviewer could approve the prompt. No record denies. Any other risky command is denied with the reason and "ask the user to run it" ([#69](https://github.com/giocaizzi/harness/issues/69); why not `PermissionRequest`: [compatibility.md](compatibility.md#decisions)). Codex sets `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA`, so the scripts run unchanged. Plugin hooks run only once trusted in `/hooks`.
- **opencode and pi in-process.** Neither runs command hooks, so `bridge.mjs` calls the handlers directly. They set no data dir: state falls back to `<tmpdir>/guard-plugin-<uid>`, as on VS Code. opencode cannot ask from a plugin, so its `config` hook appends `permission.bash` ask entries for the same prefixes (last, after `*`, so they beat a user's `allow`) and the guard leaves a covered plain command to opencode's prompt; other forms, a user `deny` on `bash` or `*` (the entries are then skipped), `opencode run --auto` in any spelling (`--auto=true`; it approves every ask) and a session with its own bash rule are denied like Codex.
- **Known limits of the borrowed prompts.** The hook cannot see `opencode run --attach <url> --auto` (the client approves; the server's argv lacks the flag): there `--auto` approves a covered plain command. Persistent approvals (Codex "don't ask again", opencode "Allow always") can cover a whole prefix for later commands. Codex on Windows wraps commands in PowerShell; its prompt rules there are untested. Details: [compatibility.md](compatibility.md#decisions). pi asks through `ctx.ui.confirm` and blocks when there is no UI (`-p`, JSON mode). Neither can block a stop: the failure is sent back as a new message once, and the next idle or settle passes. `make check` runs synchronously, so the harness waits for it.
- **Skills read, not invoked.** Codex and pi have no skill tool: a read of `skills/<name>/SKILL.md` (a read tool, or a shell reader: `cat`, `head`, `tail`, `less`, `more`, `bat`, `sed` without `-i`, `Get-Content`), a prompt starting `$name` (Codex) or `/skill:name` (pi) counts as loading it. Only a read under a skill root counts (owner decision D8): a plugin cache or install (`.claude`, `.codex`, `.copilot`, `.pi`), `~/.config/opencode`, `.agents/skills`, or a checkout's `plugins/<name>/skills`; writing or editing a `SKILL.md`, or a path elsewhere, never does. Names are stored bare, so `dev-tools:ship` and `/ship` are one skill and one `guard.skill`.
- **The mod is Claude-only.** Copilot CLI and VS Code have no mods API and no rate-limit windows, so the throttle has no Copilot side.
- **The throttle warns by default; the user picks the mode.** At 90 % of the worst plan window a spawn does what `GUARD_THROTTLE` says: `warn` (default) starts it and shows a toast, `ask` puts it in the guard's Allow/Deny dialog (parked, never called a user deny, after `GUARD_ASK_TIMEOUT_MS` or at once under `GUARD_UNATTENDED`), `deny` refuses it, `off` skips the check. A hard deny by default left reviews unrun near the limit, since the agent did the work itself instead of spawning a reviewer; the person running the session decides that trade, not the guard. The mods API gives a spawn hook no channel to the model, so `warn` reaches the person (a toast), not the agent.
- **Where a session gets the mod.** Claude Code loads it with the guard plugin, from the config dir the session runs under (`CLAUDE_CONFIG_DIR`, else `~/.claude`). A claude.ai account's plugin sync installs the account's plugins into that dir, so a headless run with its own minimal `CLAUDE_CONFIG_DIR` still gets the guard, mod included, when the account has it, even though nobody installed it there and its `installed_plugins.json` does not list it (observed 2026-10).
- **`ask` is the harness's own prompt.** Under `claude -p` or a non-interactive Copilot run nobody can answer, so the risky command does not run.
- **The skill enforcer counts the `skill` tool.** Claude's `Skill`, Copilot CLI's and VS Code's `skill` record the loaded skill; a skill read any other way is not seen, so the reminder fires once and the retry passes.

## Unattended and auto-approve runs

Hooks run before the harness applies its permission mode, so a deny holds under accept-edits, bypass, `--allow-all`, `--auto` and `-a never` alike. Only the risky-command `ask` depends on the mode.

- **`GUARD_UNATTENDED=1`** (also `true`, `on`) makes `handle` turn every risky `ask` into a deny: "Unattended run: nobody can confirm this, so the command was not run. Pick another approach, or leave it for the user." It sits before the `noAsk` branch, so it covers every harness the same way (Codex through `--no-ask`, opencode and pi through `bridge.mjs`), including a plain command a native prompt would have covered. Safe deletes (temp dirs, clean pushed or merged worktrees, merged branches and branch refs) still pass, since they never ask.
- **Set it once for the whole run.** Each hook is its own process and reads the environment the harness was started with, so a prefix on one command (`GUARD_UNATTENDED=1 git rebase …`) never reached the hooks. Two ways hold for every later tool call:
  - **The launcher** exports it in the shell that starts the harness (`GUARD_UNATTENDED=1 claude …`, `export GUARD_UNATTENDED=1` in a wrapper script, the environment of a tmux session or a CI job); every harness's hooks inherit it. For Claude Code a launcher can also put it in the `env` block of the settings it starts with (`"env": { "GUARD_UNATTENDED": "1" }` in `.claude/settings.local.json` or a `--settings` file): Claude Code applies that block to its own environment, which its Bash commands and hooks inherit (checked: with `GUARD_UNATTENDED` set only in a `--settings` file's `env`, a `PreToolUse` command hook of a `claude -p` run saw `GUARD_UNATTENDED=1`). `CLAUDE_ENV_FILE` does not work for this: it reaches later Bash commands, not hooks.
  - **The session itself:** a shell command that sets it (`export GUARD_UNATTENDED=1`, `GUARD_UNATTENDED=1 <cmd>`, `env GUARD_UNATTENDED=1 <cmd>`) counts for that command and, once the guard lets that command run, is recorded as a session fact (`{"unattended":true}` in `sessions/<id>.jsonl`): every later risky ask in that session, subagents included, becomes a deny that says a session command switched it on. Any other value (`export GUARD_UNATTENDED=0`) or `unset GUARD_UNATTENDED` records `false`. Only assignment words count: a commit message or an `echo` naming it, or an `ssh` payload setting it on another host, does not. The launcher's environment wins over a session `false`. Setting it can only turn asks into denies, so an agent opting in cannot widen what runs.
- **The Claude mod parks at once.** With `GUARD_UNATTENDED` in Claude Code's environment, the mod's ask timeout (below) parks every permission ask immediately instead of after 60 seconds, the dialog never shown, logged as `guard.ask_result` `result=unavailable` `via=unattended`. It reads only the environment, not the session fact.
- **Without it**, an interactive session waits at the first risky command until someone answers, and a headless run (`claude -p`, `copilot -p`, `codex exec`, `opencode run`, `pi -p`) cannot ask, so the command does not run. Codex under approval `never` rejects a prompt rule; `opencode run --auto` approves every ask, so the guard denies there.
- **Not verified live:** whether Claude Code's bypass mode, Copilot CLI's `--allow-all` and VS Code's auto-approve still show a hook `ask`. Treat the risky ask as unreliable there and set `GUARD_UNATTENDED=1`, which does not depend on it. (A live probe of Claude bypass was refused by the session's own auto-mode classifier, so it was not run.)
- **Other gates that can pause an overnight run:** the host guard (load over 30, CPU over 90 %, under 20 GB free) delays heavy builds and tests; the Claude-only usage throttle refuses subagents at 90 % of the plan window only under `GUARD_THROTTLE=deny` (or parks them under `ask`; the default `warn` lets them start); the stop hook runs `make check` once. Codex hooks do nothing until trusted in `/hooks`.
- **Ask timeout (Claude Code).** The mod's `tool.check` hook puts every permission ask that would reach the person (the guard's risky ask, an `ask` rule, a tool not yet allowed) in its own Allow/Deny dialog and parks it after 60 seconds without an answer, in every mode, attended included: the user may be busy in another session, and a session must not wait on a dialog. Parked means denied with "No answer: … so this call (`<command or path>`) was not run; other calls still run. This is not a refusal. Carry on with the rest of the task without it, or park it: say in your report that it is waiting for the user's approval", never "the user denied this call". It names the call, not the tool: "Bash was not run" read as "Bash is unavailable", and an unattended agent gave up its whole task. A dialog that cannot show or is dismissed (headless, a host without one) gets the same no-answer wording. Only an explicit Deny says "The user denied this call. Do not retry it or a respelling of it; ask the user what they want instead." Under `dontAsk` the mod leaves the ask to the engine, which denies anything not pre-approved. Each outcome is logged as `guard.ask_result` (`result` allow, deny, timeout or unavailable, `wait_ms`, `tool`, `tool_use_id`; `via=unattended` when `GUARD_UNATTENDED` parked it at once). `GUARD_ASK_TIMEOUT_MS` (whole milliseconds, in the environment that launches Claude Code or the `env` block of its settings) changes the wait; `0` turns the timeout off and leaves the ask to the engine's dialog; any other value keeps 60 seconds. Left to the engine: auto mode's own asks (its classifier answers them; a hook's ask in auto mode is still taken), a hosted session's asks, `AskUserQuestion` and `ExitPlanMode`. The dialog has no "always allow" and no diff preview. A failing hook falls back to the engine's dialog. The mode comes from the last prompt or tool result, so one ask right after a shift+tab mode switch can go the old way. Until the first prompt or tool result the mode is unknown: on a session's first call (`SessionStart` carries no `permission_mode`, Claude Code 2.1.310) and right after `/reload-plugins`, which starts the mod over. Then Claude Code's own asks stay with Claude Code (auto mode's classifier, `dontAsk`'s deny, or its dialog), `GUARD_UNATTENDED` included, and only a hook's ask (the guard's risky ask) is parked: parking them all denied every call of an auto-mode session after a reload, and a denied call fires no `PostToolUse` to bring the mode back ([#252](https://github.com/giocaizzi/harness/issues/252)). The cost: in default mode, the first core ask after a start or reload waits on Claude Code's dialog without the 60-second park. Claude's own questions time out natively: `askUserQuestionTimeout: "60s"` in user settings (the dotfiles set it) continues them with the answers picked so far. Other harnesses: pi and opencode can do it ([#100](https://github.com/giocaizzi/harness/issues/100)); Codex, Copilot CLI and VS Code cannot ([#101](https://github.com/giocaizzi/harness/issues/101)).
- **Agent-side rules** (worktree per task, no reliance on denied commands, report what was blocked): the `dev-tools` skill `unattended-runs`.

## Grafana

Each deny or ask, plus a sample of allows (`guard.decision`, from the command hook, with `tool_use_id` to join the harness's own tool decision), each stop check (`guard.stop`: `result` pass, fail or deferred (`why`: a timeout, a strained host or another check running), `target`, `duration_ms`; on a failure also `failed_target`, the innermost make target, and `last_line`, the output's last line with secrets masked and cut to 200 characters; the factory result gate as `target` `result-gate` with `result` block (`blocks`, the count so far), capped (a third stop let through) or error (`why`, masked: the gate failed open), and `runner` runtime or attended), each skill hint (`guard.reminder`: `rule`), each skill loaded in a session (`guard.skill`: `skill`, `via` tool or prompt; a typed `/name` counts only for this marketplace's skills, so built-in commands stay out), each answer to an ask the guard sees (`guard.ask_result`: `result` allow, deny, timeout or unavailable, `wait_ms`; from the Claude mod's dialog and from pi's confirm, where no UI is `unavailable` with `via=no-ui`; Copilot CLI and VS Code answer asks inside the harness, which reports them in its own `tool_decision`, [#158](https://github.com/giocaizzi/harness/issues/158); Codex and opencode never ask through the guard) and each spawn the usage throttle judged (`guard.throttle`, from the Claude mod: `action` warn, allow or deny, `mode` the `GUARD_THROTTLE` in force, and in ask mode `result` allow, deny, timeout or unavailable) is sent as one OTLP/HTTP log record to `$OTEL_EXPORTER_OTLP_ENDPOINT/v1/logs`. Claude Code and Copilot CLI strip `OTEL_*` from command hooks, so the hook falls back to `GUARD_OTEL_EXPORTER_OTLP_ENDPOINT`, `GUARD_OTEL_EXPORTER_OTLP_HEADERS` and `GUARD_OTEL_RESOURCE_ATTRIBUTES` from the shell that launched the harness (the dotfiles export them on personal machines with an endpoint). The Claude mod reads the same pairs (`OTEL_*`, else `GUARD_OTEL_*`). Nothing is sent when neither is set: the work machines and a VS Code started outside such a shell stay silent. The auth headers come from `OTEL_EXPORTER_OTLP_HEADERS` and are never logged; a send that fails or takes longer than 2 s is dropped and the decision stands.

`guard.decision` logs the effective action, after the harness transforms: an ask turned into a deny is `action=deny` with `via=unattended` (`GUARD_UNATTENDED`) or `via=no-ask` (Codex, opencode: no prompt covers the form), and an ask left to the harness's own prompt is `action=ask` with `via=native-ask`. It carries `cmd_hash` (12 hex characters of the sha256 of the command, whitespace collapsed) to count repeats, never the command text. A host deny (`rule=host`) carries `load1`, `cpu_percent` and `free_gb`. Allows give the ask and deny rates a denominator: one allowed command in 10 is sent as `action=allow` with `sample_rate=10` (weight each by it: `sum(sample_rate)` estimates all allows), with `via=read` for a plain read; every heavy command the host rule judged and let through (a build or test not already run through the heavy wrapper, before any host deny in the session) is sent unsampled as `rule=host` `sample_rate=1` with the host facts it passed on, while other heavy allows are sampled like the rest, so a host rule that ran and let a command through shows apart from one that never ran. Allows never go to the factory events file.

Every record carries `harness` (`claude`, `copilot`, `vscode`, `codex` from the `--harness=codex` flag the Codex hooks file passes, `opencode`, `pi`), `guard_version` (the installed plugin's) and `repo` (`owner/name` from the cwd's `origin` remote URL, else its first remote: the last two segments of a `scheme://` URL's path or of the path after the colon of `[user@]host:owner/name`, `.git` dropped, Azure's `<project>/_git/<repo>` as `project/repo`; never the host, a port, a user or a token; null for a local path, `file://` or relative remote, outside git or with no remote; read only when a record is sent, after the decision is written). The Claude mod's records (`guard.ask_result`, `guard.throttle`) carry the same three, the repo read the same way in the session's working directory. `guard.decision`, `guard.reminder`, `guard.ask_result` and `guard.stop` also carry `cmd_class`, the rule family or command family, never command text or paths: for a rule, `delete`, `git-discard`, `git-history`, `infra`, `secrets`, `opaque`, `title`, `host`, `python`, `skill`, `hint`, `routing` or `guard-error`; for an allow or an ask with no guard rule, the first program's family (`git`, `github`, `build`, `node`, `python`, `read`, `search`, `files`, …; any other program is `other`, so a private tool's name never leaves the machine); `tool` for a non-shell ask; `spawn` for a throttle; `stop` for a stop check.

The resource carries `service.name=guard` plus `OTEL_RESOURCE_ATTRIBUTES` (`service.namespace`, `host.name`). In Loki: stream labels `service_name`, `host_name`, `service_namespace`; structured metadata `rule`, `action`, `via`, `result`, `tool`, `cmd_class`, `sample_rate`, `harness`, `guard_version`, `repo`, `window`, `percent`, `source`, `plugin_version_*`.

`guard.session` is sent once per session id and harness process, at start (keyed like the session state: a resume or restart announces again, a compact does not). It carries `session_id`, `source` (Claude Code `startup`, `resume`, `clear`, `compact`) and `plugin_version_<plugin>` for every plugin of this marketplace installed for the session (non-alphanumerics as underscores, e.g. `plugin_version_dev_tools`), read the same way as the stale-plugin note (`hooks/stale.mjs` `installedVersions`; guard's own is its exact path in a versioned cache), plus the usual `harness`, `guard_version` and `repo`. Its purpose is to join Claude Code's `api_request`, which carries no plugin version, by `session_id` (agent-review's "By plugin version", [agent-review.md](agent-review.md)). The collector adds `tier` to every record. Example: `{service_name="guard"} | event_name="guard.session" | plugin_version_dev_tools="1.2.3"`.

**Factory events file.** When `FACTORY_EVENTS_FILE` is set (a factory runtime sets it for the runs it starts, [factory.md](factory.md)), each `guard.decision` is also appended to that file as one JSON line `{"ts", "decision", "rule", "cmd_hash"}`, plus `"trace_id"` and `"span_id"` under a trace context (below): `ts` ISO 8601, `decision` the effective action (`deny` or `ask`, as above), never the command text. It works in every harness, with or without an OTLP endpoint and whatever `GUARD_OTEL` says; a write that fails is dropped and the decision stands. The runtime's guard deny-rate breaker reads it.

**Trace context.** A runtime that traces a run may give the run's harness `GUARD_TRACEPARENT`, a W3C `traceparent` naming the span the run's records belong under (normally the same value as the harness's own `TRACEPARENT`; a separate variable because harnesses replace or strip trace and `OTEL_*` variables in hook environments, as they do for the `GUARD_OTEL_*` copies). When it is set and well formed, every `guard.decision` record carries the two ids:

| Field | Where | Value |
|---|---|---|
| `traceId` | OTLP log record (not an attribute) | the trace id, 32 lowercase hex |
| `spanId` | OTLP log record (not an attribute) | the span id, 16 lowercase hex |
| `trace_id` | events file line | the trace id, as above |
| `span_id` | events file line | the span id, as above |

Well formed means `00-<32 hex trace id>-<16 hex span id>-<2 hex flags>`, lowercase, surrounding whitespace trimmed, with neither id all zeros. A higher version (`01` to `fe`) is read by its first 55 characters, as W3C asks for forward compatibility, when they end the value or a `-` follows (`01-<trace id>-<span id>-01-<more>`); version `ff` is invalid, and version `00` takes nothing after the flags. When the variable is absent, empty, malformed (version `ff`, extra fields after version `00`, a wrong length, uppercase hex, a wrong separator) or names an all-zero id, the record is written without these fields, exactly as before: the guard never fails, blocks or delays a decision over it. The flags are not copied. Other records (`guard.stop`, `guard.reminder`, ...) never carry them. The guard reads only `GUARD_TRACEPARENT`, never `TRACEPARENT`, derives no trace context from anything else and starts no spans of its own. The code is the same in every harness: the variable reaches the command hooks (Claude Code, Copilot CLI, VS Code, Codex) and the in-process adapters (opencode, pi) through the process environment, so VS Code sees it only when it was started from a shell that exports it, as with the `GUARD_OTEL_*` copies ([compatibility.md](compatibility.md)). Attended sessions do not set it. Example: `GUARD_TRACEPARENT=00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01` gives `trace_id=4bf92f3577b34da6a3ce929d0e0e4736` and `span_id=00f067aa0ba902b7`.

Verify: after a denied command, `{service_name="guard"}` in Grafana Explore shows the record; `sum by (rule) (count_over_time({service_name="guard"} | rule != "" [1h]))` counts denials per rule.

`GUARD_OTEL=off` (also `0`, `false`) sends nothing, whatever the endpoint. `make test` sets it, and so must any probe that spawns `hooks/guard.mjs` or imports the engine from a shell that exports the collector: fake sessions otherwise land in the real telemetry. For the same reason `make test` empties `FACTORY_EVENTS_FILE` (empty writes nothing), and a probe run inside a factory run must too.

### Usage for opencode and pi

Neither exports telemetry, so the in-process guard reports for them, with the same endpoint and headers: one `api_request` log record per finished assistant message, as service `opencode` or `pi` (it owns `service.name` and `service.namespace`), with `session.id`, `model`, `provider`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `reasoning_tokens` and `cost_usd`. opencode prices the message itself (`cost`); pi prices it at its catalog rate (`usage.cost.total`). The names follow Claude Code's `api_request`, so one query covers every harness. Claude Code, Copilot CLI, VS Code and Codex export their own (enabled by the dotfiles); see the compatibility matrix.

## Regression corpus

`core/corpus.json` holds real commands from the guard reviews (telemetry, transcripts, code audit), paraphrased with hosts and paths anonymised and no secrets, each with the decision the guard must reach: `allow`, `allow:<hint>`, `ask:<rule>` or `deny:<rule>`, the bug id and the source. `core/corpus.test.mjs` runs each row through `evaluateCommand` with a fixed environment (`HOME=/Users/me`, a macOS `TMPDIR`) and favourable facts (every branch pushed, every regenerable name git-ignored, no linked worktree), so a row asks only where the guard cannot reach or read the facts. A row whose bug is still open runs as `todo`, so the suite stays green; the PR that fixes the bug removes its id from `OPEN` and the rows become enforced. Control rows (`control`, `probe`) are always enforced.

Every guard false ask or missed command found in telemetry (`/agent-review`) or a transcript becomes a row, with a bug id, before or with its fix.

## Troubleshooting

| Symptom | Check |
|---|---|
| No guard at all | Plugin enabled? Claude: `/plugin`; Copilot: `copilot plugin list`; VS Code: `chat.plugins.enabled`, `chat.useHooks` and the Agent Customizations editor; Codex: `codex plugin list`, then trust the hooks in `/hooks`; opencode: `~/.config/opencode/plugins/giocaizzi-guard.js` exists and points at a checkout that is still there; pi: `pi list`. `node` on PATH (22+)? Without it Copilot denies every tool call its hook covers, the others run them unguarded. |
| Codex warns `failed to parse plugin hooks config` | An old guard without a Codex-only hooks file: `codex plugin marketplace upgrade`, then re-add the plugin. |
| Every shell call denied on Copilot | The hook exits non-zero (Copilot fails `preToolUse` closed): run it by hand as above and read stderr. |
| Session never ends a turn on Copilot | `make check` keeps failing: the agent gets 8 blocks at most, then stops. |
| A factory run keeps working after it said "done" | The result gate: its `result.json` is missing or invalid. It fixes it with `write-result.mjs` or stops after two blocks; a verifier or other side session started with the run's variables sets `GUARD_RESULT_GATE=off`. |
| Machine still sleeps | Keeper running? `pgrep -fl caffeinate` / `systemd-inhibit --list`; on Linux `systemd-inhibit` needs a logind session. |
| A reminder repeats | In a subagent: skill hints count per agent, so each subagent gets one once (every harness but VS Code); the read and edit hints come once per session. Otherwise the data dir is not writable: check `sessions/<session_id>.jsonl`. |
